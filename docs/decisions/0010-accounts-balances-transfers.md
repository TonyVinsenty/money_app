## Контекст

Вкладка «Баланс» сейчас заглушка. Что про неё уже решено (ROADMAP, «Принятые решения» и «Решения по интерфейсу»):

- источники денег (банк, наличные…); при начале работы можно ввести текущие остатки (необязательно);
- источник по умолчанию для расходов; остаток меняется от операций;
- привязка операции к источнику **необязательна**, быстрый ввод остаётся «кнопка → сумма → категория»;
- источник, к которому привязаны операции, **не удаляется, а архивируется**;
- название вкладки — «Баланс»; регулярные платежи позже (этап 6) будут жить в ней же.

Что важно на сегодня:

1. **Схема v1 выпущена.** Любое изменение таблиц — только миграция v1 → v2 с тестом (`docs/how-to-migrations.md`). На iPhone уже лежат **настоящие данные**: 324 операции за 3 месяца, все без источника.
2. **CSV — единственная резервная копия** (Auto Backup выключен). Всё новое, что влияет на деньги (остатки, переводы), обязано попадать в экспорт и возвращаться импортом, иначе после потери телефона остатки будут неверными. Старые файлы экспорта (11 колонок) у пользователя уже есть — их импорт обязан работать и дальше.
3. **Займы в настоящих данных.** При переносе (шаг i.17) «поступления, которые не являются доходом, и их возврат» заведены отдельными категориями доходов и расходов — потому что перевода не было. Сейчас они раздувают итоги месяца.
4. **Идеи пользователя:** «перенос баланса в новый месяц» (окно и операция «Перенос баланса») и строка «Баланс: …» в центре кольца «Главной» с выбором в «Настройках» — обе отложены до этапа 5.
5. Ограничения прежние: local-first, деньги — целые копейки, без новых пакетов, `domain` без Flutter, шаги до ~200 строк.

## Решение

### 1. Слово в интерфейсе — «счёт» *(вопрос 1)*

В интерфейсе источник денег называется **«счёт»**: «Добавить счёт», «Счёт: Карта», «Без счёта». «Источник» неудобен для доходов: зарплата приходит *на* карту, а не *из* неё. Слово «счёт» короткое и привычное по другим приложениям учёта. Вкладка по-прежнему «Баланс». В коде — `Account`, фича `lib/features/accounts/` (так она уже названа в ADR 0002). Если пользователь выберет «источник», меняются только тексты и названия колонок CSV (п. 10), устройство не меняется.

### 2. Сущность «Счёт»

Новая таблица `accounts` (по соглашениям ADR 0001):

| Колонка | Тип | Смысл |
|---|---|---|
| `id` | `TEXT` PK | UUID v7 |
| `name` | `TEXT` | название, 1–40 символов после обрезки пробелов |
| `icon_key` | `TEXT` | ключ значка из небольшого постоянного набора (карта, наличные, банк, копилка, кошелёк, вклад, крипта, другое) — `lib/core/ui/account_icons.dart`, как у категорий |
| `currency` | `TEXT` | код валюты; `CHECK` — три заглавные латинские буквы. **Уточнено 2026-10-08 (п. 16):** любая валюта — из каталога или своя, выбирается при создании и потом не меняется; `CHECK` — 3–10 заглавных латинских букв и цифр, первая — буква |
| `currency_digits` | `INTEGER` | *(добавлено 2026-10-08, п. 16.4)* знаков после запятой у валюты счёта, 0–8; у валют каталога — как в каталоге |
| `opening_balance_minor` | `INTEGER` | стартовый остаток в копейках, **может быть отрицательным** (кредитная карта, долг) |
| `sort_order` | `INTEGER` | порядок в списке, задаёт пользователь |
| `archived_at` | `INTEGER` NULL | архив |
| `created_at`, `updated_at`, `deleted_at` | `INTEGER` | как у всех таблиц |

Правила (`domain`, тесты обязательны):

- имя не пустое, не длиннее 40 символов; **два счёта с одинаковым именем запрещены** среди не архивных — то же сравнение, что у категорий (`CategoryRule.duplicateName`: без учёта регистра, с обрезкой пробелов); при возврате из архива занятое имя — отказ и предложение переименовать;
- значок — не пустой ключ;
- **удаления нет, только архив** (как у категорий). `deleted_at` в схеме есть по соглашению, но интерфейс его не ставит. Архивный счёт пропадает из выбора в быстром вводе и из общего итога, его операции и история остаются;
- новых счетов можно сколько угодно; порядок — перестановкой (правило `reorder` то же, что у категорий, ADR 0001, дополнение вехи 2B).

**Отрицательный остаток разрешён.** В поле ввода суммы минус по-прежнему не вводится (`parseAmount` его отвергает — ADR 0004), поэтому на форме счёта рядом с суммой стоит переключатель «Минус (долг)». Знак хранится в самом числе `opening_balance_minor`: `Money` отрицательные значения допускает (ADR 0004, «Знак суммы»).

### 3. Как считается остаток

```
остаток счёта = стартовый остаток
              + доходы, привязанные к счёту
              − расходы, привязанные к счёту
              + переводы на счёт
              − переводы со счёта
```

- учитываются только живые записи (`deleted_at IS NULL`) в валюте счёта;
- дата операции **не важна**: вчерашний расход, внесённый сегодня, тоже уменьшает остаток. Поэтому «даты открытия счёта» нет (отвергнутый вариант 6);
- остаток **нигде не хранится**, а считается: один SQL-запрос с `SUM(...) GROUP BY account_id` по операциям и переводам (частичный индекс по `account_id`), окончательная арифметика — чистая функция `domain` (`computeAccountBalances`). Хранимый остаток расходился бы с историей после любой правки (отвергнутый вариант 2);
- **«Всего на счетах»** = сумма остатков **не архивных** счетов в рублях. Архивный счёт в итог не входит; не архивный счёт другой валюты тоже пропускается (сумма только в запрошенной валюте). **Уточнено 2026-10-08 (п. 16):** счета других валют больше не прячутся — «Всего на счетах» показывается отдельной строкой на каждую валюту, без пересчёта по курсу. Если отправляешь в архив счёт с ненулевым остатком, экран предупреждает: «Остаток 1 234,00 ₽ перестанет учитываться во «Всего»»;
- обновление на экране — потоком из базы (`watch`), как итоги «Главной».

### 4. Стартовый остаток — поле счёта, а не операция

Форма нового счёта спрашивает **«Сколько на счёте сейчас»** (необязательно, по умолчанию 0). Так как у нового счёта ещё нет операций, стартовый остаток = введённое число.

**«Поправить остаток»** на экране счёта: пользователь вводит, сколько денег на счёте на самом деле, приложение пересчитывает стартовый остаток так, чтобы текущий остаток стал ровно этим числом (`стартовый = введённое − движения`, чистая функция с тестом). Поправка **не создаёт операцию** и не меняет итоги месяца и «Аналитику»: разница «растворяется» в стартовом остатке. Это осознанно: расхождение обычно значит «забыл внести мелочь», и придумывать для неё доход или расход хуже (отвергнутые варианты 1 и 13).

Мастера «при первом запуске» нет: пустая вкладка «Баланс» сама предлагает добавить счёт и ввести остаток. Так это работает одинаково и у нового пользователя, и у того, у кого уже 324 операции. Отдельный мастер — если понадобится, на этапе 7.

### 5. Операция может быть привязана к счёту

- В таблицу `transactions` добавляется колонка `account_id TEXT NULL REFERENCES accounts(id)`. `NULL` — «без счёта».
- Сущность `Transaction` получает необязательное поле `accountId` и копию `withAccount(...)`.
- Репозиторий операций (вторая линия защиты, как для категорий — ADR 0001, веха 2B) проверяет: счёт существует и не удалён (`ArgumentError`), валюта счёта = валюта операции (`TransactionRule.accountCurrencyMismatch`), **новая** привязка не к архивному счёту (`TransactionRule.accountArchived`). Архивность проверяется только у изменившейся привязки: старую операцию в архивном счёте можно править. Импорт CSV (`addImported`) архивный счёт разрешает — это история.
- Смена типа операции (доход ↔ расход) в правке счёт **не сбрасывает**.

### 6. Счёт по умолчанию *(вопрос 2)*

- **Один «основной» счёт и для расходов, и для доходов** (рекомендация): зарплата обычно приходит на ту же карту, с которой тратят. Хранится в `app_settings` ключом `default_account_id` (без миграции), читается через `AppSettingsController` — как тема и «Последний экспорт».
- **Первый созданный счёт сам становится основным** — без лишнего действия. *(Уточнено 2026-10-08, п. 16.10: основным может быть только счёт в основной валюте — сам становится основным первый созданный счёт этой валюты.)* Потом основной меняется кнопкой «Сделать основным» на экране счёта; в списке у него пометка «Основной».
- Счёт ушёл в архив или ключ указывает в никуда → основного нет, новые операции сохраняются «без счёта», пока пользователь не выберет новый.
- **Быстрый ввод:** рядом с плашкой даты — такая же плашка счёта («Карта»). Основной счёт уже выбран, трогать плашку не нужно: путь остаётся «кнопка → сумма → категория» (3 действия). Тап по плашке — список не архивных счетов и «Без счёта». **Если счетов нет, плашки нет вовсе** — экран выглядит как сейчас.
- **Правка в «Истории»:** строка «Счёт» — сменить или убрать. Архивный текущий счёт показывается «Карта (в архиве)» и сохраняется, пока его не сменили.

### 7. Операции без счёта, в том числе 324 старых *(вопрос 3)*

- Миграция их **не трогает**: `account_id = NULL`, счета автоматически не создаются, ничего не угадывается.
- Они по-прежнему входят в итоги месяца, «Аналитику» и «Историю», но **не влияют ни на один остаток**. Остатки начинаются с того, что пользователь ввёл «сколько сейчас», и дальше двигаются новыми операциями (почти все — с основным счётом).
- Привязать старую операцию к счёту можно руками в правке (её сумма тогда сразу войдёт в остаток — это честное следствие формулы п. 3; при массовой привязке остаток поправляется кнопкой «Поправить остаток»).

### 8. Переводы между счетами — отдельная таблица *(вопрос 4)*

Перевод (снял наличные, пополнил вклад) — **не доход и не расход**: он меняет остатки двух счетов, но не итоги месяца. Поэтому он живёт **в своей таблице** `transfers`, а не третьим типом операции:

| Колонка | Тип | Смысл |
|---|---|---|
| `id` | `TEXT` PK | UUID v7 |
| `from_account_id`, `to_account_id` | `TEXT` FK → `accounts` | откуда и куда; `CHECK (from_account_id <> to_account_id)` |
| `amount_minor` | `INTEGER` | `CHECK (amount_minor > 0)` — пустой перевод бессмыслен |
| `currency` | `TEXT` | как у счетов |
| `occurred_on`, `occurred_at` | `INTEGER` | день и момент, как у операций (ADR 0004) |
| `note` | `TEXT` NULL | комментарий, 1–200 символов, как у операций |
| `created_at`, `updated_at`, `deleted_at` | `INTEGER` | мягкое удаление для «Отменить» |

- Переводы **не попадают** в итоги месяца, «Аналитику» и «Историю» — эти экраны и их запросы не меняются вовсе. Переводы видны на экране счёта (список «→ Наличные −5 000,00 ₽» / «← Карта +5 000,00 ₽»), там же правка и удаление с «Отменить».
- Комиссии у перевода нет: её вносят обычным расходом.
- Сущность `Transfer` и её репозиторий живут в фиче `accounts` (интерфейс `TransfersRepository` в `accounts/domain`, реализация вместе с репозиторием счетов). Правила: разные счета, сумма > 0, момент в UTC, комментарий ≤ 200, валюты совпадают, новый перевод не с/на архивный счёт.
- **Займы** (п. 3 контекста) в будущем удобно вести так же: счёт «Мне должны» (или «Долги») и переводы на него и обратно — тогда займ не раздувает доходы и расходы. Что делать со старыми категориями-займами — *вопрос 6* (рекомендация: оставить как есть). **Копилки и цели** (ROADMAP, «Продвинутое планирование») ложатся на ту же модель: копилка — обычный счёт, пополнение — перевод.

Если пользователь отложит переводы, таблица `transfers` и всё про переводы из этого ADR убираются из этапа 5, а при возвращении к ним понадобится миграция v3.

### 9. Схема v2 и миграция

`schemaVersion` 1 → 2. Шаги в `onUpgrade` (`if (from < 2)`):

1. `createTable(accounts)`;
2. `createTable(transfers)` (если переводы в этапе 5);
3. `addColumn(transactions, transactions.accountId)` — колонка объявляется **последней** в классе таблицы (после `deletedAt`), чтобы свежая база и обновлённая совпадали по порядку колонок;
4. частичные индексы: `transactions(account_id) WHERE deleted_at IS NULL AND account_id IS NOT NULL`; у `transfers` — `(occurred_on, occurred_at)`, `(from_account_id)`, `(to_account_id)`, все с `WHERE deleted_at IS NULL`.

**Данные не переносятся и не меняются.** Тест миграции: база v1 из снимка с категориями, подкатегорией, живыми и мягко удалёнными операциями, комментарием → миграция → все строки на месте байт в байт, `account_id` у всех `NULL`, новые таблицы пусты, `PRAGMA foreign_key_check` пуст. Плюс тест «свежая база = снимок v2», белый список типов (`TEXT`/`INTEGER`), проверка `CHECK` новых таблиц, `EXPLAIN QUERY PLAN` для запроса остатков.

**Миграция необратима.** Сборка с v2, однажды открывшая базу, превращает её в v2; старая сборка (`+16` и раньше) такую базу уже не откроет. Путь назад только через CSV. Поэтому перед установкой первой сборки с v2 на iPhone — обязательный экспорт (как и перед любой установкой, `docs/how-to-iphone.md`, раздел 4).

### 10. CSV: экспорт и импорт

Формат ADR 0006 **расширяется** (колонки только добавляются, ничего не переименовывается и не убирается — так ADR 0006, п. 6 и разрешает). Один файл, как и раньше.

**Колонки v2** (новые — 8, 9, 14, 15; 16–17 — п. 17):

| № | Заголовок | Значение |
|---|---|---|
| 1–7 | `Дата` … `Комментарий` | как в ADR 0006 |
| 8 | `Счёт` | имя счёта или пусто; у перевода — откуда |
| 9 | `Счёт зачисления` | только у перевода — куда |
| 10–13 | `ID операции` … `Время операции (UTC)` | как в ADR 0006 |
| 14 | `ID счёта` | id счёта (у перевода — откуда) |
| 15 | `ID счёта зачисления` | только у перевода |
| 16 | `Значок категории` | ключ значка категории (`local_cafe`, `glyph:Ж`); у `Начальный остаток` и `Перевод` — пусто. *Добавлено 2026-10-08, п. 17* |
| 17 | `Значок подкатегории` | ключ значка подкатегории или пусто (нет подкатегории, `Начальный остаток`, `Перевод`). *Добавлено 2026-10-08, п. 17* |

Человеческие колонки стоят рядом с человеческими, технические — в конце. Импорт ищет колонки по заголовку, поэтому новый порядок старым файлам не мешает. Названия колонок и новых типов фиксируются в момент первого экспорта v2 — поэтому вопрос 1 нужно решить до шага 5.16.

**Новые виды строк** (колонка `Тип`):

- `Начальный остаток` — по одной строке на **каждый** счёт (в том числе архивный и счёт без операций, иначе он пропал бы при восстановлении): `Дата` и `Время операции (UTC)` — момент создания счёта, `Сумма` — стартовый остаток со знаком (`-1500,00` для долга), `Счёт` и `ID счёта` заполнены, категория и комментарий пусты.
- `Перевод` — одна строка на перевод: `Сумма` без знака, `Счёт` → `Счёт зачисления`, `ID операции` = id перевода, комментарий.

**Экспорт** (всё или ничего, как раньше): у операции со счётом, которого нет в базе, — отказ с понятной ошибкой. Порядок строк прежний (день, момент, id).

**Импорт:**

- **Старые файлы (11 колонок) читаются как раньше**: нет колонок счёта — операции «без счёта». Тестовый набор `test/fixtures/zuno-test-dataset.csv` остаётся в формате v1 и становится сторожем совместимости: его разбор даёт ровно тот же результат, что до этапа 5, а проверка «импорт в пустую базу → экспорт» сравнивает с тем же файлом, в который вставлены пустые новые колонки.
- Все новые колонки необязательны. `Категория` остаётся обязательным **заголовком**, но ячейка у `Начальный остаток` и `Перевод` должна быть пустой (непустая — ошибка строки: так ловятся съехавшие колонки).
- **Счёт** ищется так же, как категория (ADR 0009, п. 6): по `ID счёта` (в том числе архивный) → по имени среди не архивных → **создаётся** (с id из файла, если он свободен) со стартовым остатком 0 и значком «другое». Предпросмотр перечисляет создаваемые счета: «Будут созданы счета: Карта (остаток 12 000,00 ₽), Наличные».
- `Начальный остаток`: если счёт уже есть (по id или имени) — строка пропускается как «уже есть», **остаток в базе не перезаписывается**; если нет — счёт создаётся с этим остатком и моментом создания из файла. Две такие строки на один счёт — ошибка.
- `Перевод`: оба счёта обязательны и разные, сумма > 0 (минус — ошибка); дубли — по `ID операции`, у строки без id — отпечаток (UUID v5, тот же неизменяемый `csvImportFingerprintNamespace`) из даты, суммы, обоих имён счетов, комментария и порядкового номера.
- **Отпечаток доходов и расходов не меняется** (счёт в него не входит). Иначе файлы, уже загруженные без колонки счёта, при повторной загрузке задвоились бы.
- Повторная загрузка не обновляет привязку уже загруженных операций к счёту (обновления при импорте нет — ADR 0009).
- Запись — одна транзакция: счета → категории → операции → переводы.
- Новые файлы старая сборка прочитать не сможет (не знает типов `Начальный остаток`/`Перевод`) — допустимо: сборка у пользователя всегда самая новая.
- Известная потеря при восстановлении (как у категорий): значок, порядок, отметка «в архиве» и основной счёт. Остатки и переводы восстанавливаются точно. *(Уточнено 2026-10-08, п. 17: значки категорий и подкатегорий теперь восстанавливаются; значок **счёта** по-прежнему теряется.)*
- `docs/csv-format.md` дополняется новыми колонками и типами строк.
- *Уточнено 2026-10-08 (п. 16.11):* колонка `Валюта` (она есть с ADR 0006) у каждой строки несёт её валюту, а сумма — столько знаков после запятой, сколько у этой валюты; доходы и расходы могут быть в любой обычной валюте каталога (после смены основной валюты).

### 11. «История» по счёту (дополнение к ADR 0008)

`HistoryFilter` получает необязательное поле «счёт». Ставится оно кнопкой «Операции» на экране счёта: открывается «История» с полоской «Фильтр: Счёт: Карта» и обычным «Сбросить». В лист фильтра выбор счёта в этом этапе не добавляется. Поиск и сортировка работают как прежде.

### 12. Перенос баланса в новый месяц *(вопрос 5)*

**Решено пользователем 2026-10-07: идею закрыть — ни окна, ни операции «Перенос баланса».** Слова пользователя: «Закрываем идею, пока я и сам не понимаю, что с ней делать. Потом, если что, будет возможность добавить в Настройках вариант, чтобы в Балансе в центре кольца показывался „Все Доходы минус все Расходы“, вот и перенос остатка сюда будет включен». То есть роль «переноса» играет строка «Баланс» в центре кольца в варианте «Все доходы минус все расходы» (п. 13). Доводы рекомендации: Остаток счёта переходит из месяца в месяц сам: он считается по всей истории, а не по месяцу. Операция-перенос раздула бы доходы месяца (ROADMAP, обсуждение идеи), а окно в начале месяца мешало бы быстрому вводу. Если захочется видеть «сколько было на 1-е число», это одна строка на экране счёта (остаток на начало месяца по той же формуле с отбором по дате) — отдельной задачей, когда попросят.

### 13. Строка «Баланс» в центре кольца «Главной» *(вопрос 7)*

Делается в этапе 5, последней вехой (два шага):

- в «Настройках» пункт «Строка «Баланс» на Главной» с тремя вариантами: **«Все доходы минус все расходы»** (по умолчанию — решение пользователя 2026-10-07, вопрос 7; architect рекомендовал «Сумма на счетах»), «Сумма на счетах», «Не показывать». Вариант по умолчанию виден сразу, даже без счетов: считается по всем живым операциям за всё время в выбранной валюте, включая операции без счёта; переводы в нём не участвуют (они не доход и не расход). Хранение — ключ `app_settings`, без миграции;
- в центре кольца под «Всего» (баланс месяца) — вторая, более мелкая строка «Баланс: 45 300,00 ₽». Вариант «Сумма на счетах» при отсутствии счетов строку **не показывает** (ноль был бы неправдой);
- центр уже ужимается во вписанный квадрат дырки (`FittedBox`); проверяем на 360 dp и шрифте 200 %; для скринридера подпись кольца дополняется «баланс: плюс 45 300 рублей».

### 14. `AppServices` растёт — стейт-менеджер не меняем

ADR 0002 велит вернуться к вопросу о стейт-менеджере, если в `AppScope` больше 5–6 сущностей. После этапа 5 их станет 7 (добавится `accounts`; переводы — в той же фиче, отдельным полем `transfers` или общим объектом). **Решение: остаёмся на встроенных средствах.** Условие в ADR 0002 защищало от боли «тащить зависимости руками», а её нет: `AppServices` — неизменяемый набор полей, вкладки берут из него нужное в своём `build`, тесты подставляют фейки. `provider` ничего бы здесь не упростил. Пересмотр — если появится состояние, нужное трём и более экранам и не являющееся потоком из базы.

## Последствия

**Становится проще:**

- Итоги месяца, «Аналитика», кольцо и «История» не меняются: операции без счёта и переводы им не мешают. Код этапов 2–4 почти не трогаем.
- Остаток всегда сходится с историей: он не хранится, а считается.
- Быстрый ввод не удлиняется: основной счёт выбран заранее, а без счетов экран прежний.
- Резервная копия остаётся одним файлом и восстанавливает остатки и переводы точно; старые файлы читаются.
- Займы и копилки потом ложатся на ту же модель (счёт + перевод) без новой таблицы.

**Становится сложнее:**

- Первая настоящая миграция выпущенной схемы; необратима на телефоне.
- CSV получает 4 колонки и 2 вида строк; разбор, план и запись импорта заметно усложняются (половина шагов этапа).
- Переводы не видны в «Истории» — только на экране счёта. Если пользователь захочет видеть их в общей ленте, это отдельная задача (строки другой природы в списке операций).
- Поправка остатка «молча» меняет стартовый остаток — история поправок не хранится.
- У операции ещё одна связь для проверки в репозитории (счёт: существует, архив, валюта).

**Риски:**

| Риск | Насколько вероятно | Что делаем |
|---|---|---|
| `ALTER TABLE ADD COLUMN` даёт схему, не совпадающую со снимком v2 (порядок колонок, текст ограничений в `sqlite_master`) | средне | колонка объявляется последней; тест миграции через `migrateAndValidate` скажет сразу в шаге 5.4; запасной путь — пересборка таблицы `TableMigration` из drift (тот же шаг, больше строк) |
| Установка v2 на iPhone без свежего экспорта, откат на старую сборку невозможен | низко | обязательный экспорт перед установкой (п. 9), пункт чек-листа шага 5.20 |
| Байт-в-байт тесты экспорта и тестового набора ломаются из-за новых колонок | высоко, ожидаемо | шаг 5.16 переделывает сравнение: v1-файл + пустые новые колонки; сам файл набора не меняется |
| Остатки «уплывают», потому что часть операций внесена без счёта или не на тот счёт | средне | плашка счёта видна при вводе; «Поправить остаток»; фильтр «История» по счёту |
| Центр кольца перегружен при крупном шрифте | средне | вторая строка мельче, `FittedBox`, тест на 200 % и 360 dp; вариант «Не показывать» |
| Шаги схемы и импорта больше 200 строк | средне | сгенерированные файлы не считаются; при перерасходе шаг делится (5.4a/5.4b) |

## Отвергнутые варианты

1. **Стартовый остаток — служебная операция «доход»** («Начальный остаток» в «Истории»). Попадает в доходы месяца, «Аналитику» и кольцо — итоги врут ровно на сумму остатков. Пришлось бы исключать её во всех запросах.
2. **Хранить текущий остаток колонкой счёта и обновлять при каждой операции.** Быстро читается, но расходится с историей после любой правки, удаления, «Отменить» или импорта; нужна перепроверка и починка. Подсчёт по индексу на телефоне стоит миллисекунды.
3. **Перевод — третий тип операции в `transactions`.** `category_id NOT NULL` и `CHECK (type IN (...))` требуют пересборки таблицы; каждый итог, «Аналитика», «История», фильтр, правка и CSV должны научиться исключать третий тип. Самый большой «радиус поражения» из всех вариантов.
4. **Перевод — пара операций «расход + доход» с категорией «Перевод».** Без новой таблицы, но итоги месяца раздуваются с обеих сторон, а пользователь должен помнить, что категорию нужно исключать. Ровно та проблема, что сейчас с займами.
5. **Счёт обязателен у операции / при миграции привязать все старые операции к одному счёту.** Обязательность ломает «кнопка → сумма → категория» для тех, кто счета не ведёт. Массовая привязка угадывает: часть старых трат была наличными, а сумма трёх месяцев истории сразу сдвинула бы остаток (выбор оставлен пользователю, вопрос 3).
6. **Дата открытия счёта: учитывать только операции после неё.** Вчерашний расход, внесённый после создания счёта, не уменьшил бы остаток — непредсказуемо.
7. **Основной счёт = последний использованный.** Одна поездка с наличными — и все следующие траты по умолчанию уходят в наличные. Фиксированный основной предсказуем.
8. **Отдельный CSV-файл для счетов и переводов.** Два файла легко разлучить, импорт выбирал бы два файла (тот же довод, что в ADR 0006, вариант 5).
9. **Флаг `is_default` в таблице счетов.** Нужна уникальность «ровно один основной» и миграция; ключ в `app_settings` проще и уже так хранятся тема и «Последний экспорт».
10. **«Перенос баланса» операцией «Доход: перенос» при первом запуске в новом месяце.** Раздувает доходы, требует защиты от дублей и правил на пропущенные месяцы, а остатки счетов и так переходят сами.
11. **Полное удаление счёта.** Ломает историю операций и переводов; архив решает ту же задачу, как у категорий.
12. **Галочка «учитывать во «Всего»»** (для вкладов, кредиток). Полезна, но пока не просили; добавляется позже одной колонкой с миграцией.
13. **«Поправить остаток» отдельной операцией-корректировкой.** Портит итоги месяца и «Аналитику» суммой, которой на самом деле не было в этом месяце.
14. **Переводы в «Истории» вместе с операциями уже в этом этапе.** Потребует второй вид строки в списке, в фильтре, в поиске и в сортировке «Истории» — 3–4 шага сверх плана; отложено до просьбы пользователя.

## 16. Счета в разных валютах (дополнение 2026-10-08, пересмотрено 2026-10-08)

Статус: **решение пользователя принято** (2026-10-08: вариант «а» из ROADMAP, «Отложено» → «Мультивалютность» — без курсов, «Всего» строкой на каждую валюту, внутри этапа 5). Ответы на вопросы 8 и 9 получены 2026-10-08; **ответ на вопрос 9 пользователь пересмотрел в тот же день** (слова — в «Контексте»), п. 16 переписан под это `architect` 2026-10-08. Ответ на вопрос 8 по смыслу прежний: доходы и расходы — только по счетам основной валюты. **Вопрос 10** (что происходит при смене основной валюты) ждёт ответа, рекомендация — п. 16.9; он нужен до шага 5.10m. Места, зависящие от ответов, помечены *(вопрос N)*. Шаги — 5.10d–5.10o (пачки 2В-1, 2В-2, 2В-3) и уточнения к шагам 5.11–5.27.

### Контекст

- Слова пользователя (2026-10-08): «Конвертация курсов не нужна. В разделе Баланс просто должно быть отображение сумм разных валют». Упоминалась крипта.
- Пересмотр вопроса 9 (2026-10-08), дословно: «Давай всё же расширим список валют, и соответствующих знаков валют. В принципе ограничений быть не должно, счет может быть в любой валюте/крипте, всё равно они есть только для отображения. А выбрать для списания можно только тот счет, валюта которого совпадает с основной. Можно для этого сделать в Настройках плашку „Основная валюта“».
- Сейчас (п. 3): счёт другой валюты не показывается и не входит во «Всего». Код валюты хранится у каждой суммы, счёта, перевода и операции — модель данных к этому готова.
- Но «два знака после запятой» зашиты в `parseAmount`, `AmountInputFormatter`, `formatMoney`, `formatCsvAmount`, а `spokenMoney` умеет только рубль (ADR 0004, «экспонента валюты» — отложенная задача). Символ валюты — функция `currencySymbol` (шаг 5.10c, `lib/core/format/money_format.dart`) знает три символа.
- В схеме v2 у `accounts`, `transfers` и `transactions` стоит `CHECK (currency GLOB '[A-Z][A-Z][A-Z]')`: `USDT` не пройдёт. **Схема v2 ещё не выпущена** (выпуск — шаг 5.20): таблицы `accounts` и `transfers` новые, их можно поменять прямо в снимке `drift_schema_v2.json`. Таблица `transactions` уже есть на iPhone (v1, 324 настоящие операции): поменять её `CHECK` можно только пересборкой таблицы.
- Эфир (ETH) делится до 18 знаков: 1 ETH = 10^18 минимальных единиц, а целое 64-битное число вмещает только ~9,2 · 10^18 — то есть около 9 ETH.
- Итоги месяца, кольцо, «Аналитика» и «История» сейчас только в рублях (ADR 0004, «агрегаты по одной валюте»; ADR 0007, 0008). Но методы репозитория операций (`watchAll`, `watchTotal`, `watchInPeriod`) уже принимают `currency` (по умолчанию `RUB`) — «показывать в основной валюте» значит передать туда настройку вместо константы.
- Действующих обычных (фиатных) валют в ISO 4217 около 160 (без фондовых и служебных кодов). Пакет `intl` (уже подключён) знает число знаков у каждой (`NumberFormat.currency(name:).decimalDigits`, данные CLDR), но не знает русских названий.

### Решение

*Для новичка.* **Экспонента** (в коде — `digits`) — сколько знаков после запятой у валюты: у рубля 2 (копейки), у иены 0, у кувейтского динара 3, у крипты в Zuno — 8. В базе сумма всегда целое число самых мелких единиц: 0,0015 BTC хранится как 150 000.

**16.1. Каталог валют — постоянный список в коде.** Файл `lib/core/money/currency_catalog.dart` (чистый Dart, без пакетов). Запись `CurrencyInfo`: код, `digits`, символ для экрана, название по-русски, вид (`fiat` — обычная валюта, `crypto`, `custom` — своя, п. 16.2) и необязательные три формы слова для озвучки. Содержимое:

- **все действующие обычные валюты ISO 4217** (около 160). Не входят: фондовые коды (`BOV`, `CHE`, `CHW`, `CLF`, `COU`, `MXV`, `USN`, `UYI`, `UYW`), драгметаллы и служебные X-коды (`XAU`, `XAG`, `XPD`, `XPT`, `XDR`, `XSU`, `XUA`, `XBA`–`XBD`, `XTS`, `XXX`). Региональные `XAF`, `XOF`, `XCD`, `XPF` — входят;
- **популярная крипта (11):** `BTC`, `ETH`, `USDT`, `USDC`, `TON`, `BNB`, `SOL`, `XRP`, `TRX`, `DOGE`, `LTC`. Чего нет — заводится «Своей валютой».

Размер — около 175 строк данных (одна строка — одна валюта), десяток-другой килобайт исходника; на размер приложения не влияет.

**Знаков у обычных валют — как в CLDR** (те же данные, по которым форматирует `intl`): у большинства 2, у `JPY`, `KRW`, `VND`, `ISK`, `CLP` и ещё нескольких — 0, у `KWD`, `BHD`, `OMR`, `JOD`, `TND`, `LYD` — 3. Где CLDR расходится с ISO 4217 (у `HUF`, `IDR`, `COP`, `PKR`, `IQD`, `IRR`, `LAK`, `LBP`, `MGA`, `MMK`, `KPW`, `RSD`, `SOS`, `SYP`, `YER`, `AFN`, `ALL` в CLDR 0, в ISO 2), берём CLDR — решение пользователя 2026-10-08. Тест сверяет каждую обычную валюту каталога с `NumberFormat.currency(locale: 'en', name: код).decimalDigits` — защита от опечаток без нового пакета. Во время работы каталог от `intl` **не зависит**: если новая версия `intl` поменяет число знаков, правится тест (список исключений), а каталог — никогда.

**Символ** — только там, где он однозначен и привычен: `₽`, `$` (только у `USD`), `€`, `£`, `¥` (только у `CNY`), `₸`, `₴`, `₺`, `₾`, `֏`, `₼`, `₹`, `₩`, `₪`, `฿`, `₫`, `₱`, `₦`, `₮`. У остальных (`CAD`, `AUD`, `JPY`, `CHF`, `BYN`, вся крипта, свои валюты) на экране сам код: «150,00 CAD». Список символов и русские названия («Канадский доллар», «Казахстанский тенге») — черновик, пользователь смотрит при проверке пачки 2В-2.

**Слова для озвучки** (три формы) — только у валют, чьё название — одно склоняемое слово (у «белорусского рубля» формы прилагательного и существительного расходятся, на нём правило 1/2/5 ломается): рубль (как сейчас, с копейками), доллар, евро, юань, фунт, иена, тенге, лари, драм, сум, сом, манат, биткоин, эфир. Остальные — по п. 16.6.

**Экспонента однажды выпущенной валюты не меняется никогда:** в базе лежат целые минимальные единицы, и смена «8» на «6» молча разделила бы все суммы на 100. Сторожа — сверка с `intl` (обычные валюты) и тест-снимок всех пар «код:знаков» одной строкой-константой (любая правка каталога видна в тесте).

**16.2. «Своя валюта» — для всего, чего нет в каталоге.** Последняя строка листа выбора (п. 16.8) — «Своя валюта…»: поля «Код» (правило п. 16.3, буквы сами становятся заглавными) и «Знаков после запятой» (0–8, по умолчанию 2). Название, символ и озвучка своей валюты — сам код. Правила (`domain`, тесты обязательны):

- код есть в каталоге → берётся запись каталога, введённое число знаков не используется (нельзя завести `USD` с 4 знаками);
- код уже есть у другого счёта (в том числе архивного) → знаки берутся у него, поле знаков заблокировано с подсказкой «Как у счёта «Кошелёк»» (черновик): у одного кода одна точность, иначе «Всего» и переводы сложили бы разные единицы. Проверяет и репозиторий (`AccountRule.currencyDigitsMismatch`);
- отдельно свои валюты не хранятся — они живут в счетах (п. 16.4). Группа «Ваши валюты» в листе выбора собирается из счетов;
- если когда-нибудь код своей валюты появится в каталоге с другим числом знаков — у счетов главнее знаки из базы (п. 16.4), каталог даёт только название, символ и озвучку.

**16.3. Код валюты — 3–10 заглавных латинских букв и цифр, первая — буква.** `isValidCurrencyCode` (проверка `Money`) расширяется до `^[A-Z][A-Z0-9]{2,9}$`; для операций — отдельная проверка «ровно три буквы» (`isIsoCurrencyCode`), см. 16.9–16.10. Каталог — подмножество этого правила.

**16.4. Схема v2 (не выпущена — правим её, а не делаем v3).**

- `accounts`: `CHECK (length(currency) BETWEEN 3 AND 10 AND currency GLOB '[A-Z]*' AND currency NOT GLOB '*[^A-Z0-9]*')`; **новая колонка `currency_digits INTEGER NOT NULL`** с `CHECK (currency_digits BETWEEN 0 AND 8)`, сразу после `currency` (таблица новая, порядок свободный). У валюты каталога значение равно каталогу (проверяет репозиторий), у своей — введённое.
- `transfers`: тот же `CHECK` кода; колонки знаков **нет** — перевод бывает только между счетами одной валюты, знаки берутся у счёта.
- `transactions` **не трогаем**: три буквы, без пересборки. Операции бывают только в основной валюте, а основной может быть только обычная валюта каталога — у всех них три буквы (п. 16.9). Риск для 324 настоящих операций — ноль.
- Это правка **невыпущенной** v2: `schemaVersion` остаётся 2, снимок `drift_schema_v2.json` и `test/generated_migrations/` перегенерируются, снимок v1 не меняется. Миграция v1 → v2 остаётся прежней (новые таблицы создаются `createTable` по новому описанию); тест `CHECK` дополняется: `USDT` проходит, `rub`, `US`, `1BTC`, `US-D` и 11 символов — нет; `currency_digits` −1 и 9 — нет, 0 и 8 — да.
- **Эмулятор:** его база уже v2 со старым описанием (шаг 5.4), сама она не обновится (версия та же). После шага 5.10d — экспорт CSV → очистка данных (`pm clear`) → установка → импорт; счета, созданные при проверке пачки 2, теряются (тестовые, в CSV их ещё нет). На iPhone и запасном Android v2 не ставилась — им ничего не грозит. **Начиная с 5.20 такая правка невозможна** — только v3.

**16.5. Экспонента везде, где были «две цифры».**

- `Money` не меняется: целые единицы + код. Число знаков знает `CurrencyInfo`. Функция `currencyInfoFor(код, {digits})`: код из каталога → его запись; иначе — своя валюта с переданными знаками (символ и название — код). У счёта есть своя `CurrencyInfo` (код + `currency_digits` из базы): суммы счетов и переводов показываются и вводятся через неё. Суммы операций (всегда обычная валюта каталога) — по коду. Код не из каталога без знаков — `assert` (ловится тестами в отладочном режиме), в релизе — 2 знака и код.
- `formatMoney`: знаков — по валюте; 0 знаков — без запятой (`1 500 JPY`); у обычной валюты всегда все её знаки (`12 345,67 ₽`, `150,00 $`, `12,345 KWD`); у крипты и своих валют лишние нули в конце срезаются, но остаётся не меньше двух знаков (`0,0015 BTC`, `1,00 BTC`, `−0,50 ETH`). Символ — из каталога (`currencySymbol` из 5.10c переезжает на каталог). Рубли выглядят как сейчас.
- `parseAmount(…, currency:)`: больше знаков, чем у валюты, — `tooManyDecimals`; сумма собирается целыми числами (`BigInt`) без `Money.fromMajorParts` (тот остаётся только для двух знаков). **Предел ввода — 10^14 минимальных единиц для любой валюты**: для рубля это прежний триллион, для крипты — миллион монет. Остатки сотен таких счетов складываются без переполнения.
- `AmountInputFormatter(maxDecimals:)` (при 0 запятая не вводится), `AmountFieldController(currency:)`, символ в `AmountField` и тексты ошибок поля («Не больше 8 знаков после запятой», «Не больше 1 000 000,00 BTC» — черновик) берут знаки и символ из `CurrencyInfo`.
- `formatCsvAmount`: ровно столько знаков, сколько у валюты (`0,00150000`, `1500` у иены), — точно и одинаково при каждом экспорте.

**16.6. Озвучка.** `spokenMoney`:

- рубль — без изменений («1234 рубля 50 копеек»);
- валюта со словами (п. 16.1) — число цифрами с запятой (лишние нули срезаны, без разделителя разрядов) и слово: целое — по правилу 1/2/5 («1 доллар», «2 доллара», «5 долларов»), дробное — вторая форма («12,5 доллара», «0,0015 биткоина»), минус — «минус …»;
- валюта каталога без слов — число и название через запятую: «1500, турецкая лира»;
- своя валюта — число и код: «1500, ABC». Как скринридер прочтёт код (по буквам или словом), зависит от системы; другого источника слов у своей валюты нет, а спрашивать у пользователя три формы слова — перебор.

**16.7. Вкладка «Баланс»: все счета, «Всего» по валютам.**

- `AccountsRepository.watchBalances()` без обязательной валюты: остатки **всех** счетов, каждый в своей валюте (в остаток входят только движения в валюте счёта). `computeAccountBalances` уже так умеет.
- Новая чистая функция `totalsByCurrency(счета, остатки, основная)` → «Всего» по каждой валюте, где есть хотя бы один не архивный счёт; порядок — **основная валюта первой**, остальные по коду.
- Секция показывает все не архивные счета; под «Всего на счетах» — строка на каждую валюту, знак и цвет — у каждой строки свои. Если валюта одна, экран выглядит как сейчас. Скринридер: «Всего на счетах: плюс 12 000 рублей, плюс 150 долларов, 0,0015 биткоина».
- Экран счёта, «Поправить остаток», предупреждение при архивации — в валюте счёта (маршрут берёт валюту у счёта, а не параметром).

**16.8. Выбор валюты: общий лист с поиском.**

- Виджет `lib/core/ui/currency_picker.dart` (общий: им пользуются форма счёта и «Настройки»). Сверху — поле поиска: по коду, названию и символу, без учёта регистра. Пока поиск пуст — группы: «Популярные» (`RUB`, `USD`, `EUR`, `CNY`, `BTC`, `ETH`, `USDT`, `TON` — черновик), «Ваши валюты» (свои валюты из счетов, если есть), «Все валюты» (обычные, по названию), «Криптовалюты». Последняя строка — «Своя валюта…» (п. 16.2). Ничего не нашлось — «Ничего не нашлось» и та же строка «Своя валюта…».
- Строка: название и ниже «BTC» или «USD · $»; скринридер читает «Биткоин, BTC», выбранная — признаком `selected`, без слова «выбрана» в подписи (урок шага 5.10c). Список строится лениво (`ListView.builder`): 175 строк не тормозят.
- Для основной валюты (п. 16.9) лист показывает только обычные валюты: без крипты, «Ваших валют» и «Своей валюты».
- **Новый счёт:** строка «Валюта: Российский рубль, ₽», по умолчанию — **основная валюта**. Поле «Сколько на счёте сейчас» принимает знаки по выбранной валюте. **Валюта после создания не меняется** (на форме правки — текстом, без выбора): иначе пришлось бы пересчитывать переводы. Ошиблись — в архив и создать заново. Имена счетов уникальны среди не архивных независимо от валюты.

**16.9. Основная валюта — пункт в «Настройках».**

- «Основная валюта» с подписью «Российский рубль, ₽»; тап — лист п. 16.8 (только обычные валюты). Хранится в `app_settings` ключом `main_currency` (без миграции), читается через `AppSettingsController` — как тема. По умолчанию, а также при испорченном значении или коде не из обычных валют каталога — `RUB`. У пользователя ничего не меняется, пока он сам не выберет другую.
- Основная валюта определяет: валюту новых операций (быстрый ввод); валюту итогов «Главной», кольца, «Истории» (список и итог отфильтрованного), «Аналитики» и экрана категории; какие счета можно выбрать для операции (п. 16.10); валюту по умолчанию у нового счёта; первую строку «Всего» на «Балансе»; строку «Баланс» в центре кольца (5.27).
- **Основной может быть только обычная валюта** (не крипта и не своя): у всех обычных валют код из трёх букв — `transactions` их принимает без пересборки. Крипта основной потребовала бы пересборки `transactions` (`USDT` — 4 буквы), 8 знаков в быстром вводе и «Аналитике». Если понадобится — отдельно, миграцией v3.
- **Что при смене основной валюты** *(вопрос 10, ответ пользователя 2026-10-08 — принято)*: «Главная», «История» и «Аналитика» показывают только операции **основной** валюты. Операции в прежней валюте не удаляются и не пересчитываются: остаются в базе и в экспорте CSV и снова видны, если вернуть ту валюту. Перед сменой — подтверждение (черновик): «Сделать основной валютой «Доллар США»? Главная, История и Аналитика будут показывать только операции в этой валюте. Операции в других валютах сохранятся и снова появятся, если вернуть их валюту. В быстрый ввод попадут только счета в этой валюте.» — «Сменить» / «Отмена». Основной счёт другой валюты перестаёт подставляться, но ключ не стирается — вернётся вместе с валютой.
- Правка операции — всегда в её собственной валюте (в правку попадают только операции из «Истории», то есть основной валюты, но правило от этого не зависит).

**16.10. Доходы и расходы — только по счетам основной валюты** *(вопрос 8, по смыслу без изменений)*. Счёт другой валюты меняется кнопкой «Поправить остаток» и переводами между счетами **той же** валюты. Отсюда:

- быстрый ввод (5.13) предлагает только не архивные счета основной валюты; таких нет — плашки нет;
- правка операции (5.14) — только счета валюты самой операции;
- основным счётом (5.11) может быть только счёт основной валюты: сам становится основным первый созданный счёт этой валюты; «Сделать основным» — только у них; ключ на счёт другой валюты — «основного нет»;
- кнопка «Операции» на экране счёта (5.15) — только у счетов основной валюты (в «Истории» видна только она);
- репозиторий операций уже отказывает при несовпадении валюты счёта и операции (`accountCurrencyMismatch`, шаг 5.5); операция с кодом не из трёх букв — `ArgumentError` ещё до базы;
- переводы (5.21–5.23): «Куда» — только счета той же валюты, что «Откуда»; кнопка «Перевод» видна, если есть два не архивных счёта одной валюты; обмена валют («купил доллары») нет;
- строка «Баланс» в центре кольца (5.27): «Сумма на счетах» — только счета основной валюты (нет таких — строки нет); «Все доходы минус все расходы» — только операции основной валюты.

**16.11. CSV.** Колонка `Валюта` есть с ADR 0006. **Экспорт:** у каждой строки — её валюта, сумма со всеми знаками этой валюты. **Импорт:**

- `Доход`/`Расход`: пусто (= `RUB`, как в старых файлах — не зависит от настройки) или любой код обычной валюты каталога в любом регистре; сумма — по знакам этой валюты; иначе — ошибка строки `CsvUnsupportedCurrency`. Так операции в долларах после смены основной валюты восстанавливаются из копии;
- `Начальный остаток`/`Перевод`: пусто (= `RUB`), код каталога, код своей валюты, которая уже есть у счёта в базе (знаки — оттуда), или **новый код своей валюты** — тогда знаки = число цифр после запятой в его строке `Начальный остаток` (0–8; экспорт всегда пишет все знаки, поэтому восстановление точное). Перевод в новой своей валюте без строки `Начальный остаток` — ошибка строки; неверный код (п. 16.3) — тоже;
- создаваемый счёт получает валюту и знаки своей строки `Начальный остаток`, без неё — `RUB`; найденный по id или имени счёт другой валюты — ошибка строки «валюта не совпадает со счётом «Карта» (USD)» (черновик); операция в валюте, не совпадающей со счётом, — та же ошибка;
- отпечатки доходов и расходов не меняются; в отпечаток перевода входит валюта.

`docs/csv-format.md` получает правило валют, пример строки `Начальный остаток` в `USDT` и в своей валюте.

### Последствия

**Проще и лучше:**

- Пользователь видит все свои деньги в любой валюте и крипте — каждые в своей валюте, без выдуманного курса.
- Пока основная валюта — рубль, итоги месяца, «Аналитика», «История» и быстрый ввод выглядят как сейчас.
- Переезд в другую страну не требует нового приложения: основная валюта меняется в «Настройках», старые операции не теряются.
- Знаки после запятой — в одном месте (`CurrencyInfo`); «двойка» исчезает из разбора, формата и озвучки.
- Схема меняется «бесплатно»: v2 ещё не выпущена, миграции v3 нет, `transactions` не пересобирается.
- Новых пакетов нет: каталог — константы, сверка знаков — уже подключённым `intl`.

**Сложнее и хуже:**

- Пачка 2В — 12 шагов вместо 5 (каталог из ~175 валют, лист с поиском, своя валюта, основная валюта) и уточнения к 9 шагам дальше по плану; CSV-импорт получает развилку «валюта строки и счёта» и вывод знаков своей валюты из строки `Начальный остаток`.
- Трата с долларовой карты при основном рубле не вносится операцией — только «Поправить остаток» и переводы *(вопрос 8)*.
- Эфир точен до 8 знаков; своя валюта озвучивается кодом.
- Русские названия ~160 валют пишутся руками — возможны неудачные названия (не опасно: название не влияет на суммы).
- При смене основной валюты операции прежней валюты пропадают из «Истории» и итогов до возврата валюты — нужно предупреждение *(вопрос 10)*.
- Эмулятор придётся один раз очистить и загрузить данные из CSV.

**Риски:**

| Риск | Насколько вероятно | Что делаем |
|---|---|---|
| Кто-то поменяет экспоненту уже выпущенной валюты | низко | сверка с `intl` и тест-снимок «код:знаков» всего каталога; комментарий в каталоге |
| Опечатка в числе знаков при наборе ~160 валют | средне | та же сверка с `intl` — ловит каждую обычную валюту |
| Своя валюта заведена с одним числом знаков, второй счёт того же кода — с другим | низко | правило п. 16.2 в `domain` и в репозитории; поле знаков блокируется |
| Правка схемы v2 (`CHECK`, `currency_digits`) забыта до 5.20 | низко | первый шаг пачки (5.10d); в чек-листе 5.20 — «снимок v2 последний раз проверен» |
| Переделка `formatMoney`/`parseAmount` меняет вид рублей | средне | все прежние тесты формата, разбора, поля и CSV остаются как есть и обязаны быть зелёными; новый код — ветка для знаков ≠ 2 |
| Где-то сумма счёта своей валюты показана без её `CurrencyInfo` (2 знака вместо 4) | средне | `assert` на код не из каталога без знаков; виджет-тесты экранов со счётом своей валюты (4 знака) |
| Пользователь сменил основную валюту и «потерял» операции | средне | подтверждение со словами «сохранятся и снова появятся»; возврат валюты всё показывает; экспорт содержит всё |
| Длинная крипто-сумма не влезает в строку счёта при крупном шрифте | средне | срез лишних нулей; тест на 360 dp и 200 %; сумма в строке переносится/ужимается как сейчас |

### Отвергнутые варианты

1. **Только короткий фиксированный список из 7 валют** (первый ответ на вопрос 9). Пересмотрен пользователем 2026-10-08: «ограничений быть не должно».
2. **Только каталог, без своей валюты** (так было в первой редакции п. 16). Любая новая монета ждала бы новой сборки; пользователь хочет «любую валюту/крипту».
3. **Своя валюта без выбора знаков** (всегда 2 или всегда 8). 2 знака не дают ввести 0,0001 монеты; 8 знаков у «условных единиц» — лишние нули. Поле 0–8 стоит одну строку формы.
4. **Отдельная таблица своих валют** (`custom_currencies`: код, знаки, название). Ещё одна таблица, правка и архив, валюты-«сироты» без счетов, ещё одна сущность в CSV. Колонка у счёта даёт то же: своя валюта существует, пока есть счёт в ней.
5. **Своя валюта в `app_settings`** (JSON). База не проверяет, в CSV не попадает — после восстановления знаки потеряны.
6. **Брать число знаков из `intl` во время работы.** Обновление пакета молча поменяло бы смысл сохранённых сумм. `intl` — только для сверки в тесте.
7. **18 знаков для эфира: хранить суммы `BigInt` текстом или двумя колонками.** `SUM` в SQLite перестаёт работать, `Money` и все подсчёты переписываются. Ради «пыли» после 8-го знака — несоразмерно.
8. **`double` для крипты.** Запрещено принципом 4 (деньги — никогда `double`).
9. **Крипта или своя валюта основной; пересобрать `transactions` в v1 → v2 под коды до 10 символов.** Риск для 324 настоящих операций без пользы сейчас; позже (v3) стоит столько же.
10. **Запретить смену основной валюты, пока есть операции.** Пользователь с историей (уже 324 операции) не сменит её никогда, кроме как удалив данные.
11. **«История» и итоги во всех валютах сразу.** Итог отфильтрованного списка и сортировка по сумме смешали бы рубли с долларами; «Аналитика» по нескольким валютам — отдельное кольцо на каждую. Несоразмерно без курсов.
12. **Миграция v3 вместо правки v2.** Нужна была бы, только если v2 уже на телефоне; сейчас — лишняя миграция с тестом.
13. **«Всего ≈ … ₽» по курсу, ввод курса руками или загрузка из сети.** Отвергнуто пользователем; сеть противоречит local-first без отдельного решения.
14. **Разрешить смену валюты счёта.** Переводы и стартовый остаток в старых единицах стали бы бессмысленными; пересчитывать — значит выдумывать курс.

## 17. Значки категорий в CSV v2 (дополнение 2026-10-08)

### Контекст

Мини-пачка «Иконки» (`docs/ROADMAP.md`, «5B-И», шаги 5.15e–5.15l) даёт около 80 значков Material, буквы (`glyph:Ж`, `glyph:D`) и цифры, смену значка у категории и свой значок у подкатегории. Значок (`icon_key`) в CSV не попадал: после восстановления из файла в пустое приложение у категорий пользователя был бы «Другое». CSV — единственная резервная копия, а значки — ручная работа пользователя. Формат v2 ещё не выпущен (выпуск — шаг 5.20), поэтому колонки можно добавить сейчас без отдельной версии. Пользователь выбрал вариант в5-б (2026-10-08).

### Решение

1. **Две новые колонки в конце** (после `ID счёта зачисления`): 16 — `Значок категории`, 17 — `Значок подкатегории`. В конце, а не рядом с `Категория`: это техническое значение (ключ, а не текст для человека), и номера колонок 1–15 из п. 10 не сдвигаются. Импорт всё равно ищет колонки по заголовку.
2. **Значение — ключ как он хранится в базе**: `local_cafe`, `more_horiz`, `glyph:Ж`, `glyph:5`. Экспорт пишет ключ без проверки (даже незнакомый — например, из будущей версии), чтобы файл не терял информацию.
3. **Какие строки заполнены.** `Доход`/`Расход`: `Значок категории` — всегда; `Значок подкатегории` — если у операции есть подкатегория, иначе пусто. `Начальный остаток`, `Перевод`: обе ячейки пусты.
4. **Импорт: разбор.** Обе колонки необязательны; ячейка обрезается по краям, пустая = «нет значка». Ячейки значков **никогда не дают ошибку строки** (у `Начальный остаток`/`Перевод` непустой значок просто игнорируется) — неверный значок не стоит отказа от всего файла.
5. **Импорт: план.** Значок берётся **только для категорий и подкатегорий, которые импорт создаёт**: ключ из файла, если он известен приложению; пустой или неизвестный — «Другое» (`csvImportCategoryIconKey`, `more_horiz`), как сейчас. Если строки одной новой категории несут разные значки — берётся из первой по порядку файла (тот же порядок, что «первое появление» категории). **Существующая категория (найдена по id или имени) значок не меняет** — импорт не обновляет данные (ADR 0009). Значок в отпечаток строки **не входит** (отпечаток не меняется, п. 10).
6. **Где проверяется «известный ключ».** Список значков живёт в `lib/core/ui/category_icons.dart` (там Flutter), а `planCsvImport` — в `domain` (чистый Dart). Поэтому план получает параметр-функцию `bool Function(String iconKey) isKnownIconKey` (обязательный); экран импорта (`presentation`) передаёт `isKnownCategoryIconKey` из `core/ui`. Так `domain` не зависит от Flutter, а тесты плана подставляют свой список.
7. **Старые файлы.** CSV v1 (11 колонок) и v2 без колонок значков читаются как раньше: создаваемые категории получают «Другое».

### Последствия

- CSV v2 — 17 колонок вместо 15; шаги 5.16–5.18 растут примерно на 60 строк (если шаг не влезает в ~200 строк — делится, 5.16a/5.16b и т. д.).
- Восстановление из файла в пустое приложение возвращает значки категорий и подкатегорий; значок счёта, порядок, архив и основной счёт по-прежнему теряются (п. 10).
- Побайтная проверка «тестовый набор v1 → импорт в пустую базу → экспорт» больше не может сравнивать с «v1 + пустые новые колонки»: импорт v1 создаёт категории с `more_horiz`, и экспорт пишет этот ключ. Тест сравнивает файл без колонок 16–17 с «v1 + пустые колонки счёта», а колонки значков проверяет отдельно (ключ = значок категории в базе).
- `docs/csv-format.md` (шаг 5.19) описывает обе колонки и правило «только для создаваемых категорий».
- Знакомые ключи — общие с приложением: значок, добавленный в будущей версии, старая сборка при импорте заменит на «Другое» (сборка у пользователя всегда самая новая — допустимо).

### Отвергнутые варианты

1. **Не писать значки в CSV** (вариант в5-а). После восстановления пользователь выбирал бы значки заново — для единственной резервной копии это потеря ручной работы.
2. **Колонки значков рядом с `Категория`/`Подкатегория`.** Человеку удобнее видеть, но сдвигает номера колонок 8–15 из п. 10 и мешает читать файл в Excel: ключ `local_cafe` — не текст для человека.
3. **Импорт обновляет значок существующей категории.** Импорт в ADR 0009 ничего не обновляет; иначе повторная загрузка старого файла молча откатила бы значок, выбранный позже.
4. **Неизвестный ключ — ошибка строки.** Файл из более новой версии не загрузился бы целиком из-за украшения.
5. **Сохранять неизвестный ключ как есть** (приложение нарисует запасной значок «Категория»). Пользователь выбрал «Другое» — тот же значок, что у категорий из импорта сейчас; незнакомый ключ в базе к тому же не выбирается в сетке.
6. **Проверять ключ в `domain` по своему списку.** Два списка значков разойдутся; функция-параметр обходится без дубля.

**Дополнение (2026-10-09, ревью шага 5.18, решение пользователя).** Пометка «в архиве» в CSV v2 по-прежнему не пишется (колонку «В архиве» не добавляем). Строки `Начальный остаток` считаются дублями только по `ID счёта` (по имени — лишь у строк без id), поэтому архивная и активная «Карта» с разными id — два счёта. Если при импорте имя занято другим не архивным счётом, новый счёт создаётся с суффиксом «Карта (2)», «(3)»… (первое свободное, основа обрезается до 40 символов вместе с суффиксом); оба счёта активные, лишний пользователь архивирует сам. Строка с заполненным `ID счёта`, которого нет в приложении, по имени счёт не ищет — создаёт новый (с суффиксом, если имя занято); пустой `Счёт` при ненайденном id — ошибка строки «счёт с ID «…» не найден». Отвергнуто: колонка «В архиве» (точнее, но расширяет формат; пользователь выбрал проще).
