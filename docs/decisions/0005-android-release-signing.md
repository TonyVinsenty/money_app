# 0005. Подпись релизной сборки Android

- Статус: принято (пользователем, 2026-09-22)
- Дата: 2026-09-22

Связанные решения: [0001](0001-local-storage-drift.md) (файл базы на устройстве, Auto Backup выключен), [0003](0003-dependencies.md) (пакеты; этап 3 новых пакетов не добавляет). План этапа 3 — в `docs/ROADMAP.md`, раздел «Этап 3 — шаги».

## Контекст

Этап 3 — первая установка приложения на **настоящий Android-телефон**. До сих пор оно жило только на эмуляторе в отладочной сборке.

Что есть сейчас. В `android/app/build.gradle.kts` лежит строка из шаблона `flutter create`:

```kotlin
buildTypes {
    release {
        // TODO: Add your own signing config for the release build.
        signingConfig = signingConfigs.getByName("debug")
    }
}
```

То есть релизная сборка подписывается **отладочным** ключом. Отладочный ключ (`~/.android/debug.keystore`) Flutter создаёт сам, он одинаков для всех проектов на машине, его пароль общеизвестен (`android`), на другой машине он **другой**, а Google Play такие APK не принимает в принципе.

Почему это важно именно сейчас, а не «когда-нибудь при публикации»:

- **Android разрешает обновить установленное приложение, только если новая версия подписана тем же ключом.** Подпись сменилась — система откажет в установке поверх, придётся удалять приложение, а вместе с ним и все данные.
- **Auto Backup у нас выключен** (решение пользователя, см. ADR 0001): копии данных в Google-аккаунте нет. Значит «удалить и поставить заново» = потерять всё, что введено.
- **Ключ нельзя сгенерировать заново.** Потерян ключ — потеряна возможность обновлять именно это приложение. Поэтому ключ создаётся один раз, в начале этапа 3, и хранится бережно.

Ограничения, в которых принимается решение:

- `CLAUDE.md`, раздел «Соглашения»: секреты и ключи подписи (`.env*`, `key.properties`, `*.jks`, `*.keystore`) **не читать, не создавать в репозитории и не коммитить**; это же запрещено в `.claude/settings.json` и `.gitignore`. Значит, ни один агент не может ни создать ключ, ни увидеть пароли.
- Разработчик работает на Windows, один, на личной машине; публикации в Google Play пока нет, CI для Android тоже нет.
- Приложение local-first: никакой облачной инфраструктуры, где можно было бы держать секреты, у проекта нет.

## Решение

### 1. Ключ создаёт пользователь сам и хранит вне репозитория

Хранилище ключей (`zuno-release.jks`, RSA 2048, срок 10 000 дней) пользователь создаёт один раз командой `keytool` из комплекта JDK и кладёт **вне каталога проекта** — например, в `D:\Android\keys\`. Пошаговая инструкция пишется в `docs/how-to-android-release.md` (шаг 3.1).

Агенты ключ **не создают, не читают, не копируют и не показывают** — это прямое правило `CLAUDE.md`. Всё, что делает `flutter-developer`, — правка Gradle, которая знает только *путь* к файлу с настройками, но не сами пароли.

### 2. Пароли — в отдельном properties-файле рядом с ключом

Файл `zuno-keystore.properties` (тоже вне репозитория, рядом с ключом) содержит четыре строки:

```properties
storeFile=D:\\Android\\keys\\zuno-release.jks
storePassword=...
keyAlias=zuno
keyPassword=...
```

Это стандартный для Android формат. Новое здесь — только его местоположение: не внутри репозитория.

### 3. Путь к этому файлу Gradle берёт из переменной окружения `ZUNO_KEYSTORE_PROPERTIES`

Решение пользователя от 2026-09-22. Переменная задаётся один раз в пользовательских переменных Windows (там же, где уже живут `ANDROID_HOME`, `GRADLE_USER_HOME`, `ANDROID_AVD_HOME`) и хранит **полный путь** к properties-файлу.

Что это даёт: в репозитории нет ни ключа, ни паролей, ни даже пути к ним. Настройка новой машины — одна переменная окружения и копия двух файлов из резервной копии.

### 4. Нет ключа — нет релизной сборки (но отладочная работает как раньше)

`signingConfigs` для `release` заполняется, только если переменная задана, файл по этому пути существует и читается. Иначе:

- `flutter build apk --release` и `flutter build appbundle` **останавливаются с понятным сообщением** вида «Не найден файл с параметрами ключа подписи. Задайте переменную окружения ZUNO_KEYSTORE_PROPERTIES — см. docs/how-to-android-release.md». Молча подписать релиз отладочным ключом нельзя: это ровно та ошибка, которая обнаружится через полгода, когда обновление перестанет ставиться;
- отладочные и профильные сборки (`flutter run`, `flutter build apk --debug`, запуск на эмуляторе, тесты) работают **без всякой переменной**, как сегодня. Это важно: отладочная сборка используется каждый день, и ломать её ради релиза нельзя.

### 5. Сторож-тест против возврата отладочной подписи

Добавляется маленький тест (в духе уже существующих сторожей чистоты `core` и границ слоёв): он читает текст `android/app/build.gradle.kts` и падает, если в блоке `release` снова появилась отладочная подпись (`signingConfigs.getByName("debug")`). Так «временная» строка из шаблона не вернётся незаметно при будущем обновлении Flutter или при правке Gradle.

### 6. Номер версии и номер сборки

`versionName` и `versionCode` по-прежнему берутся из `pubspec.yaml` (`version: X.Y.Z+N`), как это делает шаблон Flutter. Правило: **каждая сборка, которую ставим на телефон, увеличивает `+N`**, иначе Android откажется ставить её поверх предыдущей. Версия на время этапа 3 — `0.1.0+N`; `1.0.0` появится в этапе 7 («версия 1.0 для себя»).

### 7. Резервная копия ключа — обязанность пользователя

Ключ и properties-файл копируются **минимум в два места** (например, менеджер паролей и внешний диск или архив в облачном хранилище пользователя). Это записывается в инструкцию `docs/how-to-android-release.md` отдельным пунктом с объяснением последствий потери.

### 8. Play App Signing — отдельное решение позже

Когда дойдёт до публикации в Google Play, там действует своя схема: Google хранит ключ подписи приложения, а разработчик подписывает загружаемый файл «ключом загрузки» (upload key). Сейчас это не нужно и ничего не меняет: сегодняшний ключ при публикации станет либо ключом приложения, либо ключом загрузки. Решение принимаем отдельным ADR в тот момент, когда публикация будет реальной задачей.

## Последствия

**Становится проще:**

- APK на телефоне — настоящий релиз: его можно обновлять поверх, не теряя данные (а других резервных копий у нас до мини-этапа «Экспорт CSV» и нет);
- в репозитории по-прежнему ноль секретов, правило `CLAUDE.md` соблюдено буквально: агенты не прикасаются ни к ключу, ни к паролям;
- настройка на новой машине — одна переменная окружения, а не правка файлов проекта;
- ошибка «релиз подписан отладочным ключом» стала невозможной: сборка упадёт, а сторож-тест не даст вернуть строку из шаблона.

**Становится сложнее:**

- на машине без переменной окружения релизная сборка не соберётся — это осознанный отказ, а не баг (сообщение объясняет, что делать);
- появляется ручная ответственность: ключ нужно хранить и не терять; напоминание живёт в инструкции;
- будущий CI (облачная iOS-сборка или GitHub Actions для Android) потребует другого способа доставки ключа — секрет CI, который перед сборкой записывается во временный файл. Это доработка одного места в Gradle, архитектуру не меняет.

**Риски:**

| Риск | Вероятность | Что делаем |
|---|---|---|
| Ключ потерян (переустановка Windows, сломался диск) | средняя | правило «две копии» в инструкции; напоминание в шаге 3.1 |
| Пароль лежит в открытом виде в файле на диске | принимаем | машина личная, файл вне репозитория; полноценное шифрование секретов для проекта из одного разработчика — лишняя сложность |
| Переменная окружения не видна оболочке (задана, но не подхвачена) | высокая при первой настройке | в инструкции — проверка `echo $env:ZUNO_KEYSTORE_PROPERTIES` и напоминание перезапустить терминал и Android Studio |
| Забыли поднять `+N` и обновление не ставится | высокая | правило записано в инструкции; ошибка Android при установке понятная |

## Отвергнутые варианты

**1. Оставить отладочную подпись «пока не публикуемся».** Самый дешёвый путь: ничего не делать. Отвергнут: отладочный ключ разный на разных машинах, общеизвестный по паролю и не принимается Google Play; а главное — как только телефон начнёт использоваться по-настоящему, смена подписи будет означать переустановку с потерей данных. Ключ дешевле завести сейчас, на пустой базе.

**2. `key.properties` внутри `android/`, как советует документация Flutter.** Стандартный и самый распространённый вариант: файл с паролями лежит в каталоге проекта и добавлен в `.gitignore`. Отвергнут: файл с секретами внутри репозитория рано или поздно уезжает в коммит (`git add -A` после правки `.gitignore`, копирование каталога, архив проекта), а наше правило из `CLAUDE.md` прямо запрещает создавать `key.properties` в репозитории. Вынести файл наружу стоит одну строку в Gradle.

**3. Хранить все четыре значения в переменных окружения** (`ZUNO_STORE_FILE`, `ZUNO_STORE_PASSWORD`, `ZUNO_KEY_ALIAS`, `ZUNO_KEY_PASSWORD`). Рабочий вариант, по безопасности равноценный: пароль в переменной окружения виден любому процессу пользователя так же, как файл на диске. Отвергнут ради простоты: четыре переменные вместо одной, их легко рассинхронизировать и неудобно переносить на другую машину. Остаётся запасным вариантом для будущего CI, где секреты приходят именно переменными.

**4. Play App Signing уже сейчас.** Отвергнут как преждевременный: публикации нет, а схема с ключом загрузки добавляет сущностей, смысл которых виден только в магазине.

**5. Зашифрованный ключ в репозитории** (например, `gpg`-архив плюс пароль в голове). Отвергнут: для одного разработчика на одной машине это сложность без выигрыша — пароль от архива всё равно где-то хранится, а забытый пароль означает ту же потерю ключа.
