## Контекст

Этап 4 добавляет итоги за день/неделю/месяц/год/свой интервал, кольцевую диаграмму расходов по категориям (на вкладке «Аналитика» и на «Главной» за текущий месяц) и разбивку по подкатегориям. Уже решено пользователем (ROADMAP, «Пожелание пользователя: расширенная „Главная“»):

- на «Главной» — **кольцо**, в центре **баланс месяца** (доходы минус расходы за этот месяц) — *с 2026-10-04 подпись «Всего» вместо «Баланс», число то же — баланс месяца, см. «Уточнения 2026-10-04»*;
- сектора **меньше 3 %** объединяются в группу **«Остальное»** (не путать с категорией «Прочее»);
- зажал палец на секторе — сектор подсвечен; отпустил на нём — открывается «Аналитика» этой категории; отпустил мимо — ничего;
- подкатегорий на кольце «Главной» нет, разбивка по ним — в «Аналитике».

Открытых архитектурных вопросов три:

1. **Чем рисовать диаграмму** — своим кодом или пакетом (ADR 0003 отложил решение до этого этапа).
2. **Где считать итоги** — запросом SQL с группировкой (`GROUP BY`) или чистыми функциями в `domain` над списком операций.
3. **Как округлять проценты**, чтобы их сумма была ровно 100 %.

Слово для новичка: **`CustomPainter`** — встроенный класс Flutter, которому дают «холст» (`Canvas`), а он рисует на нём линии и дуги. Пакеты для этого не нужны.

## Решение

### 1. Диаграмма — свой `CustomPainter`, без пакетов

Виджет кольца `DonutChart` живёт в `lib/core/ui/` (так предписывает дополнение к ADR 0002: его используют и «Главная», и «Аналитика», и экран категории). Виджет **ничего не знает** про категории и деньги: он получает список сегментов «вес (целое число) + цвет», номер подсвеченного сегмента и виджет для центра кольца. Внутри — три части:

| Часть | Что делает | Как тестируется |
|---|---|---|
| рисование | дуги `Canvas.drawArc` толстой линией, зазор 2 dp между секторами цветом фона, подсвеченный сектор толще | widget-тест «рисуется без ошибок, размер верный» (скриншотные «золотые» тесты не используем: шрифты на Windows и телефоне разные) |
| попадание пальцем | чистая функция `sectorIndexAt(точка, размер, веса)`: перевод точки в угол (отсчёт от «12 часов» по часовой стрелке), `null` в дырке кольца и за его краем | юнит-тесты без виджетов: углы на границах секторов, центр, край, один сектор, нулевые веса |
| касания | нажатие подсвечивает сектор; отпускание на секторе вызывает `onSelect`; отпускание мимо или начало прокрутки — снимает подсветку (*уточнено 2026-10-04: подсветка следует за пальцем с первого касания, отменяет только реальная прокрутка — см. «Уточнения 2026-10-04»*) | widget-тесты с `tester.startGesture` / `moveTo` / `up` |

Дробные числа (`double`) появляются **только** внутри виджета — при переводе целых весов в углы для рисования. Это ровно то исключение, которое разрешает ADR 0004 («доли для диаграммы идут только в картинку, никогда обратно в сумму»).

Оценка объёма: рисование и попадание ~150 строк, касания ~80 строк, плюс тесты — 2 шага по нашим правилам (шаги 4.7 и 4.8).

**Проверено на pub.dev 2026-10-04: `fl_chart` 1.2.0** (издатель flchart.dev ✓, около 7,1 тыс. лайков, 150 points, 1,88 млн загрузок, лицензия MIT, последний выпуск полгода назад; зависимости `flutter`, `equatable`, `vector_math`; нативного кода нет). Кольцо умеет (`centerSpaceRadius`), касания тоже (`PieTouchData.touchCallback`). В документации круговой диаграммы **ничего не сказано про доступность** (семантику для скринридера).

Почему всё-таки свой код:

- нам нужна **одна** диаграмма одного типа; пакет тянет ещё пять видов графиков и две транзитивные зависимости;
- наш жест особенный («зажал — подсветилось — отпустил — открылось, отпустил мимо — отмена»), и под него проще написать 80 строк, чем подстраивать чужой `touchCallback`;
- доступность мы делаем **списком рядом**, а не семантикой картинки, — пакет тут ничего не даёт;
- внешний вид (зазоры, толщина, баланс в центре) подгоняется под `design-style.md` точно;
- никаких новых загрузок: шаги этапа 4 **не требуют выключать VPN**;
- ADR 0003 так и предлагал: «сначала своя диаграмма, `fl_chart` — запасной вариант, если своё съест больше двух шагов».

**Запасной вариант.** Если шаги 4.7–4.8 не уложатся в два шага по ~200 строк, `flutter-developer` останавливается, а architect выносит `fl_chart` на решение пользователя. Пакет добавляется **только с явного согласия пользователя**, отдельным шагом с чекпоинтом (ADR 0003, CLAUDE.md). Замена локальна: меняется только `lib/core/ui/donut_chart.dart`, подсчёты в `domain` не трогаются.

### 2. Итоги считаются в `domain` по списку операций периода

Новая фича `lib/features/analytics/` — только `domain` и `presentation`. Папки `data` **нет** (уточнение к дереву ADR 0002, где у `analytics` был задуман `data` с запросами `GROUP BY`).

- **Репозиторий операций** получает один новый метод: `watchInPeriod({period, currency})` — поток «живых» операций за период (обе границы включительно, только указанная валюта, по возрастанию дня, момента и `id`). Валюта отбирается в запросе `WHERE currency = ?` — правило ADR 0004 соблюдено.
- **Все подсчёты — чистые функции** в `lib/features/analytics/domain/` (без Flutter, без базы):
  - `summarizePeriod(операции, период)` → доходы, расходы, баланс (доходы минус расходы, может быть отрицательным), количество операций;
  - `totalsByCategory(операции, период, тип)` → суммы по категориям верхнего уровня, по убыванию;
  - `subcategoryTotals(операции, период, категория)` → суммы по подкатегориям плюс строка «без подкатегории»;
  - `percentShares(суммы)` → целые проценты (см. п. 3);
  - `chartSlices(итоги по категориям)` → сектора кольца с группой «Остальное» (см. п. 4).
- Функции сами отбирают операции по периоду (`DateRange.contains`), поэтому им можно подать любой список — например, весь тестовый набор `test/fixtures/test_dataset_two_months.csv`.
- Смешение валют в одном списке — `ArgumentError` (его и так бросает `Money` при сложении), на это есть тест.

Почему так, а не `GROUP BY` в SQL:

- **Тестируемость.** Подсчёты проверяются обычными юнит-тестами на тестовом наборе (131 операция), без базы. Сверка «сумма по категориям = итог месяца» пишется в три строки.
- **Один запрос на экран.** Экрану аналитики нужны и итоги, и категории, и подкатегории за один и тот же период — всё считается из одного списка, данные между карточками не могут разойтись.
- **`AppServices` не растёт.** Отдельный репозиторий аналитики стал бы шестой сущностью в `AppScope` — это граница пересмотра стейт-менеджмента в ADR 0002. Новый метод в существующем репозитории её не трогает.
- **Объёмы маленькие.** Личные траты — порядка 100–300 операций в месяц, несколько тысяч в год. Список за год собирается за миллисекунды; на телефоне это не заметно.

Чтобы итоги «Аналитики» и карточек «Главной» (они считаются `watchTotal` в SQL) не разошлись, в шаге 4.5 есть сверочный тест: тестовый набор загружается в базу в памяти, и `summarizePeriod(watchInPeriod(...))` обязан совпасть с `watchTotal` по обоим типам и с суммами, зафиксированными в `test/fixtures/test_dataset_two_months_test.dart`.

**Когда пересмотреть:** если на реальных данных экран года начнёт заметно тормозить (больше ~20 тыс. операций за период) — переносим агрегаты в SQL отдельным шагом. Сигнатуры функций `domain` при этом сохранятся.

### 3. Проценты — целые, методом наибольшего остатка, сумма ровно 100

Процент — это только подпись на экране; суммы остаются целыми копейками. Считаем **целочисленно**, без `double`:

1. для каждой суммы `a` при общем итоге `T`: целая часть `(a × 100) ~/ T`, остаток `(a × 100) % T`;
2. недостающие до 100 единицы раздаём по одной строкам с **наибольшими остатками**; при равных остатках — строке, которая выше в списке (она крупнее);
3. итог `T = 0` (нет расходов или все нулевые) — процентов нет, строки показываются без них.

Пример: три одинаковые суммы → 34 %, 33 %, 33 % (а не 33 + 33 + 33 = 99). Это тот же метод, что `Money.allocate` из ADR 0004, только для процентов.

Переполнения нет: предельная сумма одной операции 1 000 000 000 000 ₽ = 10^14 копеек, `× 100` = 10^16 — далеко до предела 64-битного целого (~9,2 × 10^18).

Если у категории сумма больше нуля, а округлённый процент 0, на экране пишем **«<1 %»** (честнее, чем «0 %»). В расчёте её значение 0, поэтому сумма чисел остаётся 100.

**Проценты считаются один раз — для полного списка категорий.** Процент сектора «Остальное» — сумма процентов входящих в него категорий. Так число на секторе и числа в списке всегда согласованы.

### 4. Сектора кольца, «Остальное» и цвета

- Категория «мелкая», если `сумма × 100 < итог × 3` (ровно 3 % — уже не мелкая). Сравнение целочисленное.
- Мелкие категории объединяются в «Остальное», **только если их две и больше**: одну мелкую показываем как есть, группировать её бессмысленно.
- **Не больше 8 именных секторов** (по размеру палитры). Если крупных категорий больше восьми, хвост тоже уходит в «Остальное».
- **«Остальное» никогда не состоит из одной категории** (уточнено 2026-10-04 по ревью вехи 4A): если после предела 8 секторов в группе оказалась ровно одна категория, к ней уходит и последний именной сектор (7 именных + «Остальное» из двух). Если мелкие все категории, кольцо — один сектор «Остальное» 100 % (на практике нужно 34 и больше категорий).
- **Цвет — по месту сектора** (самый крупный — первый цвет палитры и т. д.), «Остальное» — нейтральный серый. Так у соседних секторов цвета всегда разные. Цена: при смене периода у одной и той же категории может смениться цвет. Это приемлемо, потому что цвет на экране всегда стоит рядом с названием (в списке и легенде) — его не нужно запоминать.
- Палитра — 8 цветов для светлой и тёмной темы в `AppColors` (`ThemeExtension`, как уже сделаны цвета расхода и дохода). Требования: контраст каждого цвета с фоном карточки не ниже **3:1** (норма WCAG для графических элементов), без «смысловых» красного и зелёного (по `design-style.md` они значат только «расход» и «доход»). Проверяется тестом через `test/support/contrast.dart`.
- Строки мелких категорий в списке получают серую метку — того же цвета, что сектор «Остальное».
- Сектор «Остальное» на «Главной» подсвечивается при нажатии, но **никуда не ведёт** (все мелкие категории видны в списке на вкладке «Аналитика»).

### 5. Доступность: смысл не только цветом и не только картинкой

- Само кольцо для скринридера — **один узел с короткой подписью** («Диаграмма расходов за октябрь. Всего: плюс 12345 рублей»; число — баланс месяца); сектора по отдельности скринридер не перебирает.
- Рядом с кольцом всегда есть **список строк**: метка цвета, иконка категории, название, сумма, процент. Каждая строка — кнопка, читается целиком: «Продукты, 12345 рублей 50 копеек, 34 процента» (сумма — через `spokenMoney`, число без пробелов). Иконка и метка цвета исключены из семантики.
- На «Главной» список короткий (легенда, до 4 строк), на «Аналитике» — полный.
- Суммы — через `formatMoney`/`spokenMoney`, знак «+»/«−» у баланса, цвет только у суммы (ADR 0004, `design-style.md`).

### 6. Период

- Виды: день, неделя (с понедельника, `weekRange`), месяц, год, свой интервал (обе границы включительно, `DateRange`).
- По умолчанию при открытии вкладки — **текущий месяц**. «Сегодня» берётся из `Clock` (в тестах — фиксированная дата).
- Стрелки «назад/вперёд» сдвигают период на один такой же; **вперёд нельзя дальше текущего периода**: будущих операций не бывает (ADR 0004, «будущие операции заранее не создаются»). У своего интервала стрелок нет; конец интервала не позже сегодняшнего дня.
- Состояние выбора периода — `AnalyticsController extends ChangeNotifier` (ADR 0002); правила сдвига периода — чистые функции в `analytics/domain`.
- Как и на «Главной», «сегодня» фиксируется при создании вкладки: если приложение открыто через полночь, вкладка узнает о новом дне при пересоздании. Это уже принятое упрощение.

## Последствия

**Становится проще:**

- ни одного нового пакета и ни одной новой загрузки — этап 4 не зависит от VPN;
- все подсчёты проверяются юнит-тестами на тестовом наборе, без экранов и без базы;
- «Главная», «Аналитика» и экран категории используют одно кольцо и одни функции подсчёта — числа совпадают везде;
- `AppScope` не растёт, миграции базы не нужны (новый метод только читает существующую таблицу по существующему индексу `occurred_on`).

**Становится сложнее:**

- свой виджет кольца (~230 строк) поддерживаем сами;
- новый метод в `TransactionsRepository` требует обновить тестовые фейки (`test/support/fakes.dart`, фейк в тесте экспорта);
- итоги карточек «Главной» по-прежнему считаются SQL-запросом `watchTotal`, а «Аналитика» — в `domain`. Два способа подсчёта сверяет тест шага 4.5; объединять их сейчас незачем.

**Риски:**

| Риск | Что делаем |
|---|---|
| Касания кольца конфликтуют с прокруткой «Главной» | жест построен на `GestureDetector` (нажатие и долгое нажатие); если палец поехал как прокрутка, нажатие отменяется и подсветка снимается — это отдельный тест шага 4.8. *С шага 4.11b — `Listener`; отмена только при реальном сдвиге позиции `Scrollable` родителя (см. «Уточнения 2026-10-04»)* |
| Цвета соседних секторов неразличимы для людей с нарушением цветового зрения | зазор между секторами, подписи в списке, иконки категорий; цвет никогда не единственный носитель смысла |
| Длинные подписи и крупный шрифт (200 %) ломают экран на 360 dp | в каждом шаге с экраном — widget-тест на шрифт 200 % без переполнения |
| Своё кольцо съедает больше двух шагов | остановка и вопрос пользователю про `fl_chart` (см. п. 1) |
| Год с тысячами операций тормозит | замер на телефоне при закрытии этапа; при необходимости — агрегаты в SQL отдельным шагом |

## Отвергнутые варианты

**1. Пакет `fl_chart` сразу.** Рабочий вариант с низким риском (чистый Dart, без нативного кода). Отвергнут по принципу «минимум зависимостей»: нам нужна одна диаграмма, а жест и доступность всё равно пишем сами. Остаётся запасным (см. п. 1) — только с согласием пользователя.

**2. Агрегаты в SQL (`GROUP BY category_id`) в новом `AnalyticsRepository`.** Быстрее на очень больших объёмах, но: шестая сущность в `AppScope`, три-четыре новых запроса с тестами плана выполнения, подсчёты проверяются только через базу. При наших объёмах выигрыша нет. Можно вернуться к нему без переделки экранов.

**3. Проценты с десятыми (34,2 %).** Точнее, но на маленьком экране шумнее, и всё равно нужно правило «сумма = 100,0». Целые проценты с «<1 %» читаются проще. Если пользователь выберет десятые — меняется одна функция (`× 1000` вместо `× 100`).

**4. Обычное округление каждого процента отдельно.** Даёт 99 % или 101 % в сумме — пользователь это замечает и перестаёт доверять цифрам.

**5. Постоянный цвет у каждой категории.** Удобно запоминать, но в схеме v1 цвета у категории нет (решение этапа 2), значит нужна миграция и выбор цвета в настройках. Цвет по порядку категории (`sortOrder`) без миграции даёт одинаковые цвета у соседних секторов. Отложено: можно добавить позже необязательной колонкой.

**6. Подписи процентов прямо на секторах.** На узких секторах не помещаются, при крупном шрифте наезжают друг на друга. Цифры живут в списке рядом.

**7. Семантика для каждого сектора (`CustomPainter.semanticsBuilder`).** Скринридер читал бы сектора по одному, но прямоугольники касания для дуг получаются неточными, а список рядом даёт то же самое надёжнее.
