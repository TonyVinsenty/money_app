# 0002. Управление состоянием и структура каталогов

- Статус: принято (пользователем, 2026-09-19)
- Дата: 2026-09-19

Связанные решения: [0001](0001-local-storage-drift.md) (хранилище), [0003](0003-dependencies.md) (пакеты), [0004](0004-money-dates-recurring.md) (деньги, даты, регулярные платежи).

## Контекст

`CLAUDE.md` задаёт рамку заранее: состояние — встроенные средства Flutter
(`ValueNotifier`/`ChangeNotifier`/`ListenableBuilder`), пока ADR не обоснует иное; слои
`domain → data → presentation`; структура по возможностям (feature-first), общее — в
`lib/core/`. Нужно это либо подтвердить, либо аргументированно заменить, и заодно зафиксировать
конкретное дерево папок под функции из `docs/ROADMAP.md`: categories, transactions, accounts,
analytics, recurring, settings, export.

Важный вход из [0001](0001-local-storage-drift.md): drift отдаёт данные потоками (`watch()`),
которые сами перестраиваются после записи в базу. Значительная часть «состояния» в приложении
учёта расходов — это просто данные из базы, и их не нужно дублировать в памяти.

## Решение

### Управление состоянием: подтверждаем встроенные средства Flutter

Пакеты `provider`, `riverpod`, `bloc`, `get_it`, `flutter_hooks` **не добавляем**.
Работаем так:

| Что за состояние | Чем делаем | Пример |
|---|---|---|
| Данные из базы (списки, итоги, остатки) | `StreamBuilder` над drift-потоком, либо `Future` + `FutureBuilder` | список операций, сумма за месяц |
| Состояние одного экрана/формы | `StatefulWidget` + `setState`, `TextEditingController` | форма добавления расхода |
| Одно значение, нужное нескольким виджетам одного экрана | `ValueNotifier<T>` + `ValueListenableBuilder` | выбранная категория, выбранный период |
| Объект с несколькими полями и методами (контроллер экрана) | класс `extends ChangeNotifier` + `ListenableBuilder` | контроллер экрана аналитики |
| Глобальные настройки приложения | один `AppSettingsController extends ChangeNotifier`, отданный вниз через `InheritedNotifier` | тема (светлая/тёмная), первый день недели, валюта по умолчанию |
| Доступ к базе и репозиториям | обычный `InheritedWidget` (`AppScope`) в корне, созданный один раз в `main()` | `AppScope.of(context).transactionsRepository` |

Правила, чтобы это не превратилось в кашу:

1. **Кто создал — тот и `dispose()`.** Любой `ValueNotifier`/`ChangeNotifier`, созданный в
   `State`, освобождается в `dispose()`. Это самая частая утечка у новичков.
2. **Контроллеры экранов не импортируют Flutter-виджеты.** `ChangeNotifier` — это
   `package:flutter/foundation.dart`, он в `presentation`, но про `BuildContext` не знает:
   так его можно тестировать обычным юнит-тестом без `pumpWidget`.
3. **Репозитории передаются параметром конструктора**, а не берутся из глобальной переменной.
   Тогда в тесте подставляется fake-репозиторий без всякого DI-пакета.
4. **Никаких `setState` в `build`** и никакой бизнес-логики в виджетах: подсчёты — в `domain`,
   запросы — в `data`.

### Где встроенных средств будет не хватать (и что мы с этим сделаем)

Честно перечисляю места, где будет неудобно, чтобы это не стало сюрпризом:

- **Передача зависимостей вглубь дерева.** Нет `context.read<T>()`, придётся либо тащить
  объект через конструкторы, либо написать свой `InheritedWidget`. Решение: один `AppScope`
  на всё приложение (~40 строк, пишется один раз) — этого достаточно для базы, репозиториев
  и настроек.
- **Общий кэш между экранами.** Если два экрана независимо подписались на одни и те же
  данные, будет два запроса в базу. Для локальной SQLite на телефоне это не проблема
  (запросы миллисекундные), поэтому кэш не строим. Пересмотреть — только если появится
  измеренная тормознутость.
- **Гранулярность перестроений в больших списках.** `ListenableBuilder` вокруг всего экрана
  перестраивает экран целиком. Решение: оборачивать в `ListenableBuilder`/`ValueListenableBuilder`
  как можно более мелкие куски дерева, списки строить `ListView.builder`.
- **Асинхронные состояния «загрузка / ошибка / данные»** руками пишутся в каждом
  `StreamBuilder` (`snapshot.hasError`, `snapshot.hasData`, иначе спиннер). Решение: один
  маленький общий виджет `AsyncView<T>` в `lib/core/ui/`, чтобы не копировать это на каждом
  экране.
- **Undo/redo и сложные межэкранные сценарии.** Пока их нет. Если на этапе 7 понадобится
  что-то вроде «отменить удаление» на нескольких экранах — это повод вернуться к вопросу,
  но, скорее всего, хватит `SnackBar` с действием и мягкого удаления из 0001.

**Условие для пересмотра.** Возвращаемся к вопросу о стейт-менеджере, если на этапе 4 или 5
окажется, что: один и тот же кусок состояния нужен трём и более экранам одновременно, **или**
`AppScope` разросся так, что в нём больше пяти-шести сущностей. Тогда пишем новый ADR и
рассматриваем `provider` (самый тонкий слой поверх `InheritedWidget`) как минимальный шаг.

### Слои

```
domain      чистый Dart, БЕЗ import 'package:flutter/...'
            сущности (Transaction, Category, Account, Money),
            правила (подсчёт итогов, правило повторения),
            интерфейсы репозиториев (abstract class TransactionsRepository)

data        drift-таблицы, DAO, реализации репозиториев,
            маппинг «строка базы ↔ доменная сущность»

presentation  экраны, виджеты, контроллеры (ChangeNotifier), форматирование для показа
```

Зависимости идут **только внутрь**: `presentation → domain`, `data → domain`.
`domain` не знает ни о drift, ни о Flutter. Проверка простая и её стоит выполнять глазами
на каждом ревью: в любом файле внутри `domain/` не должно быть слова `drift` и
`package:flutter` (кроме, возможно, `package:flutter/foundation.dart` ради `@immutable` —
но лучше обойтись без него).

Правила по дереву:

- Внутри `features/<feature>/` всегда ровно три папки: `domain`, `data`, `presentation`.
  Пустую папку не создаём заранее — добавляем, когда появляется первый файл.
- Фича **не импортирует** `presentation` или `data` другой фичи. Допустимо импортировать
  чужой `domain` (например, `transactions` знает про `Category`). Если два `presentation`
  тянутся друг к другу — общий кусок переезжает в `lib/core/ui/`.
- Всё, что нужно двум и более фичам и не является сущностью предметной области, живёт в
  `lib/core/`.
- `test/` зеркалит `lib/`, имя файла = имя тестируемого файла + `_test.dart`.

## Последствия

**Становится проще:**

- Ноль пакетов на состояние — меньше версий, меньше «магии», меньше того, что может
  устареть. Для новичка встроенные средства ещё и лучше документированы.
- Контроллеры на `ChangeNotifier` тестируются обычным `test()` без Flutter-окружения.
- Дерево каталогов заранее описано на все этапы: добавляя функцию, разработчик не
  придумывает, куда её положить.

**Становится сложнее:**

- Зависимости передаются руками: конструкторы будут длиннее, чем при `context.read<T>()`.
- Придётся один раз написать свой `AppScope` и `AsyncView` (~80 строк на двоих).
- Дисциплина `dispose()` полностью на разработчике: забытый `dispose` = утечка, которую
  Flutter не подсветит.

**Риски для новичка:**

| Риск | Что делаем |
|---|---|
| Утечки из-за забытого `dispose()` | правило «создал в `State` — освободи в `dispose`»; включить lint `close_sinks`/`cancel_subscriptions` в `analysis_options.yaml` |
| Логика уехала в виджеты | `qa-reviewer` проверяет: в `presentation` нет вычислений над деньгами и датами |
| Лишние перестроения на большом списке | `ListView.builder` + узкие `ValueListenableBuilder`; оптимизируем только по факту тормозов |
| «А вдруг встроенного не хватит» | условие пересмотра описано выше; переход на `provider` не потребует переписывать `domain` и `data` |

## Отвергнутые варианты

### `provider`

Тонкая обёртка над `InheritedWidget`, почти стандарт де-факто, чистый Dart без нативного кода.
Отвергнут **на сейчас**: единственное, что он нам даёт сверх встроенного, — это удобный
`context.read/watch`, а весь нужный объём DI закрывается одним самописным `AppScope`.
Добавить его позже — несложно и не потребует переписывать слои. Первый кандидат, если
встроенных средств перестанет хватать.

### `flutter_bloc` / `riverpod`

Мощнее и дисциплинированнее, но обе библиотеки приносят собственную модель мышления
(события/состояния у bloc, провайдеры и кодогенерация у riverpod). Для разработчика-новичка
это второй большой концептуальный слой поверх Flutter, который придётся учить одновременно
с самим Flutter. При этом наш объём состояния маленький: значительная часть «состояния» —
просто поток из базы. Отвергнуты как несоразмерные задаче.

### Слои по типам вместо feature-first (`lib/screens`, `lib/models`, `lib/services`)

Проще на старте, но к этапу 6 папка `screens/` превращается в свалку из двух десятков
файлов от разных функций, а связанные файлы лежат в разных концах проекта. Отвергнуто;
кроме того, feature-first уже зафиксирован в `CLAUDE.md`.

### Отдельные Dart-пакеты под каждый слой (мультипакетный репозиторий)

Жёстко запрещает `domain` импортировать Flutter — компилятор бы это сам проверял.
Отвергнуто: для одного разработчика это лишние `pubspec.yaml`, настройка путей и
усложнение сборки. Возвращаемся к идее, только если `domain` начнёт «протекать»
на практике.

## Дополнение 2026-09-20: составные экраны

  («принято, 2026-09-19») относится к основному решению и этим дополнением не меняется.
- Дата: 2026-09-20

### Контекст дополнения

После решений по интерфейсу от 2026-09-20 (см. `docs/ROADMAP.md`) появились экраны, которые
собираются из кусочков **разных** фич:

- **главный экран** — кнопки «+» и «−» (ввод операции живёт в `transactions`) плюс круговая
  диаграмма расходов за текущий месяц (данные считает `analytics`);
- **вкладка «Баланс»** — список источников денег (`accounts`) и регулярные платежи (`recurring`);
- **«Настройки»** ведут на экран, где пользователь задаёт порядок плиток в сетке категорий
  (`categories`).

Основное решение запрещает фиче импортировать `presentation` или `data` другой фичи.
Непонятно, кому такие составные экраны принадлежат, поэтому фиксируем правила заранее —
иначе на этапе 2 дерево каталогов расползётся.

### Решение

**1. Главный экран — своя фича `features/home/presentation/`.**
Это экран, а не предметная область, поэтому у `home` есть только папка `presentation`
(`domain` и `data` не создаём — создавать пустые папки основное решение и так запрещает).
`home` собирает: две свои кнопки «+»/«−» и виджет диаграммы. Сам **виджет** диаграммы (только
рисование: получает готовый список «категория — сумма — цвет» и рисует круг) переезжает в
`lib/core/ui/` — тогда его одинаково используют и главный экран, и вкладка «Аналитика», и
никто не импортирует чужой `presentation`. Данные для диаграммы `home` берёт из `analytics/domain`
(чужой `domain` импортировать можно) через репозиторий из `AppScope`.

**2. Вкладка «Баланс» — контейнер живёт в `lib/app/`, а не в `features/balance/`.**
Контейнер (`lib/app/balance_tab.dart`) показывает друг под другом две публичные секции:
`AccountsSection` из `features/accounts/presentation/` и `RecurringSection` из
`features/recurring/presentation/`.

*Почему именно так (это решение архитектора, а не слова пользователя).* Если завести фичу
`features/balance/`, то она обязана импортировать `presentation` сразу двух чужих фич —
прямое нарушение правила из основного решения. Переносить же обе секции в `lib/core/ui/`
неправильно: они не «общие мелкие виджеты», а полноценные куски своих предметных областей.
Выход: правило «фича не импортирует чужой `presentation`» действует **между фичами**, а
`lib/app/` — это не фича, а слой сборки приложения: он и так знает про все фичи, потому что
создаёт `AppScope`, темы и навигацию. Поэтому собирать чужие секции в одном экране разрешено
**только** коду в `lib/app/`, и только «в одну сторону»: `app/` знает про фичи, фичи про `app/`
не знают. `accounts` и `recurring` при этом друг о друге по-прежнему не знают.

Каждая секция — обычный публичный виджет своей фичи (`AccountsSection`, `RecurringSection`),
который сам умеет показать себя без экрана-хозяина: берёт репозиторий из `AppScope`,
рисует заголовок и содержимое. Пока экран «Баланс» один, этого достаточно.

**3. Экран порядка категорий — в `features/categories/presentation/`, переход через маршрут.**
Экран принадлежит `categories` (он про категории, а не про настройки). «Настройки» открывают
его по **именованному маршруту**, который зарегистрирован в `lib/app/` (таблица маршрутов
`MaterialApp`), а не прямым импортом класса экрана.

Общее правило: **переход на экран чужой фичи делается через маршрут, объявленный в `lib/app/`.**
Тогда фича знает только строку-имя маршрута, а кто на неё отзовётся — забота `app/`. Это же
правило закрывает кнопки главного экрана: «+» и «−» открывают форму быстрого ввода из
`transactions` маршрутом, а не импортом.

**4. Быстрый ввод: тип операции — параметр.**
В дереве `features/transactions/presentation/quick_add/` форма получает тип операции
(`income` / `expense`) **параметром** — его задаёт нажатая на главном экране кнопка. Переключателя
«Доход | Расход» внутри формы нет. Менять и удалять записи можно в `history/` + `edit/` — это
основной и единственный путь правки.

**5. Заметка про порядок сетки категорий (для этапа 2).**
Пользователь задаёт порядок плиток сам, поэтому порядок — это свойство самой категории:
столбец `sortOrder` (целое число) в таблице категорий, сортировка `ORDER BY sortOrder`.
Отдельную таблицу «порядок» не заводим. Это заметка к контексту
[ADR 0001](0001-local-storage-drift.md); сам ADR 0001 здесь не изменяется — столбец появится
вместе с таблицей категорий на этапе 2.

### Последствия

- Дерево каталогов пополняется одной папкой `features/home/presentation/` и файлом
  `lib/app/balance_tab.dart`; виджет диаграммы заранее кладём в `lib/core/ui/`, а не в `analytics`.
- Фичи остаются независимыми: `accounts`, `recurring`, `transactions`, `categories` друг друга
  не импортируют. Связи собираются в одном месте — `lib/app/`.
- Цена: `lib/app/` будет расти и станет «местом, где всё сходится». Если он разбухнет
  (скажем, больше 5–6 составных экранов), это повод вынести маршруты в отдельный файл
  `lib/app/routes.dart` и вернуться к вопросу новым ADR.
- Переход по строке-маршруту слабее проверяется компилятором, чем прямой импорт: опечатку в
  имени маршрута видно только при запуске. Смягчаем тем, что имена маршрутов — константы в
  одном файле в `lib/app/`.
- Секции «Баланса» придётся сразу писать как самостоятельные виджеты (без предположений об
  экране-хозяине) — чуть больше дисциплины при написании.

### Отвергнутые варианты (к дополнению)

- **Фича `features/balance/` с импортом `presentation` из `accounts` и `recurring`.** Самое
  очевидное решение и самое вредное: прямо нарушает правило основного решения и связывает
  три фичи между собой. Отвергнуто.
- **Перенести секции источников и регулярных платежей в `lib/core/ui/`.** Формально правило
  соблюдено, но `core` превратится в свалку из кусков предметных областей, а `core` должен
  оставаться нейтральным (деньги, даты, мелкие виджеты). Отвергнуто.
- **Главный экран внутри `features/transactions/presentation/`.** Кажется удобным (кнопки же
  про операции), но тогда `transactions` начнёт тянуть диаграмму и данные аналитики, то есть
  станет «фичей обо всём». Отвергнуто в пользу отдельной `home`.
- **Переключатель «Доход | Расход» внутри формы быстрого ввода.** Отвергнут: пользователь
  явно решил, что тип задаёт нажатая кнопка, а лишний переключатель добавляет касание в
  самый частый сценарий.
