# 0001. Локальное хранилище: SQLite через drift

- Статус: принято (пользователем, 2026-09-19)
- Дата: 2026-09-19
- Решено: используем drift с кодогенерацией; сгенерированные файлы `*.g.dart` **коммитим** в репозиторий.

Связанные решения: [0002](0002-state-management-and-project-structure.md) (состояние и структура), [0003](0003-dependencies.md) (пакеты), [0004](0004-money-dates-recurring.md) (деньги, даты, регулярные платежи).

## Контекст

MoneyAPP — local-first: единственный источник истины лежит на телефоне, сети и аккаунта нет
(`CLAUDE.md`, «Принципы»). `CLAUDE.md` уже фиксирует «реляционная локальная БД (SQLite),
схема версионируется, для каждой миграции есть тест». Открытый вопрос — **каким способом**
работать с SQLite.

Что от хранилища требуется по `docs/ROADMAP.md`:

1. **Реляционные запросы с агрегатами** по интервалам дат и категориям
   (итоги за день/неделю/месяц/год/свой интервал, круговая диаграмма по категориям, этап 4);
   плюс статистика частоты категорий по времени суток для подсказок (этап 6).
2. **Миграции схемы** — схема будет расти этап за этапом (категории → операции → источники
   денег → регулярные платежи), при этом данные пользователя терять нельзя.
3. **Тестируемость на in-memory БД** — по `CLAUDE.md` слой `data` покрывается тестами
   репозиториев и тестами миграций. Тесты должны идти на Windows командой `flutter test`,
   без эмулятора.
4. **UUID-идентификаторы**, поля `createdAt`/`updatedAt`, мягкое удаление — задел под
   будущий совместный бюджет на двоих.
5. **Деньги — целые копейки + код валюты** (`INTEGER` + `TEXT`), никаких `double`/`REAL`.

Ограничения разработчика: новичок, Windows, Mac нет. iOS собирается только в облачном CI,
локально проверить iOS **нельзя**. Поэтому каждая зависимость с нативным кодом — это риск:
поломка вылезет не на машине разработчика, а в облачной сборке или, хуже, в рантайме на iPhone.

## Решение

### Выбираем drift

Берём **drift** (`drift` + генератор `drift_dev` + `build_runner` в dev-зависимостях).
Движок SQLite приходит из пакета `sqlite3`, который drift использует под капотом.

Проверено на pub.dev 2026-09-19:

| Пакет | Версия | Издатель | Лайки | Pub points | Загрузки | Опубликован |
|---|---|---|---|---|---|---|
| `drift` | 2.35.0 | simonbinder.eu (проверенный) | 2470 | 160 | 1.3 млн | 9 дней назад |
| `drift_dev` | 2.35.0 | simonbinder.eu | 72 | 110 | 1.02 млн | 9 дней назад |
| `sqlite3` | 3.6.0 | simonbinder.eu | 463 | 150 | 2.52 млн | 5 дней назад |
| `build_runner` | 2.16.1 | tools.dart.dev | 2360 | 160 | 6.56 млн/нед | 17 дней назад |

Платформы drift: Android, iOS, Linux, macOS, Web, Windows. Лицензия MIT.

Важный факт с pub.dev: **`sqlite3` версии 3.x сам поставляет нативный SQLite** через
build hooks — на странице пакета написано, что «because this library uses hooks, it bundles
SQLite with your application and doesn't require any external dependencies or build
configuration». Из-за этого пакет `sqlite3_flutter_libs` устарел: его страница прямо
говорит, что «starting from version 0.6.0, this package no longer does anything», последняя
версия помечена `0.6.0+eol`. То есть **ручной правки `Podfile`/`build.gradle` под SQLite
не требуется** — это заметно снижает iOS-риск, которого мы боялись.

Чего мы **не** берём: `drift_flutter` (0.3.1, 67 лайков, 424 тыс. загрузок) — удобная обёртка
на одну строку, но она тянет за собой `path_provider`, `sqlite3_flutter_libs` (eol) и
`sqlcipher_flutter_libs` (шифрование, которое нам не нужно). Открыть базу вручную — это
примерно 10 строк кода, а `path_provider` нам всё равно понадобится для экспорта CSV.
`drift_flutter` остаётся **запасным вариантом**, если ручное открытие базы не заведётся
в облачной iOS-сборке.

### Как устроим работу с базой

- Таблицы описываются классами Dart в `lib/core/database/tables/`, drift генерирует
  типизированный код (`app_database.g.dart`). Генерация — `dart run build_runner build`.
- Класс базы `AppDatabase` принимает `QueryExecutor` **параметром конструктора**, а не
  создаёт его сам. Это прямое требование для тестов: в приложении передаём файловую базу,
  в тестах — `NativeDatabase.memory()`.
- `schemaVersion` растёт на каждое изменение схемы, миграции пишутся в `MigrationStrategy`.
  На каждую миграцию — тест (см. «Тестирование» ниже).
- Включаем `PRAGMA foreign_keys = ON` в `beforeOpen` (SQLite по умолчанию их не проверяет).
- Репозитории (`data`) отдают наружу доменные объекты, drift-классы за границу `data` не
  вылезают. Интерфейсы репозиториев живут в `domain`.

### Соглашения по схеме (обязательны для всех таблиц с данными пользователя)

| Колонка | Тип в SQLite | Что это |
|---|---|---|
| `id` | `TEXT` PRIMARY KEY | UUID (версия 7 — см. 0003), генерируется в `domain`/`data`, не базой |
| `created_at` | `INTEGER` | момент создания, UTC, миллисекунды эпохи |
| `updated_at` | `INTEGER` | момент последнего изменения, UTC, миллисекунды эпохи |
| `deleted_at` | `INTEGER` NULL | мягкое удаление: `NULL` = живая запись |

- Денежные суммы: `amount_minor INTEGER NOT NULL` + `currency TEXT NOT NULL` (см. 0004).
  Тип `REAL` в схеме запрещён.
- Все «живые» выборки идут через индексы с условием `deleted_at IS NULL`.
- Для дат операций — отдельная колонка локальной календарной даты (см. 0004), по ней
  строятся индексы для агрегатов.

### Тестирование

- **Репозитории**: `NativeDatabase.memory()` в `setUp`, `close()` в `tearDown`. Каждый тест
  получает чистую базу — это быстро и не оставляет мусора на диске.
- **Миграции**: у `drift_dev` есть инструмент выгрузки схемы по версиям
  (`dart run drift_dev schema dump` / `steps`), из которого генерируются хелперы для
  тестов «база версии N → миграция → база версии N+1, данные на месте». Точный набор команд
  проверяем на этапе 2, когда появится первая реальная миграция; до этого момента
  считаем это «планируемым», а не «проверенным».
- **Виджет-тесты**: по документации drift в виджет-тестах базу надо отдавать через
  `DatabaseConnection` с `closeStreamsSynchronously: true`, иначе тест падает на «висящих»
  таймерах.
- **Проверено 2026-09-20 (шаг 2.1 этапа 2):** пакет `sqlite3` 3.6.0 работает в `flutter test` на
  Windows **без ручной установки `sqlite3.dll`** и в сборке Android (x86_64). Механизм: build hook
  пакета скачивает готовую библиотеку с релизов GitHub (`simolus3/sqlite3.dart`, с проверкой хэша)
  в `.dart_tool/hooks_runner/`; поэтому на чистой машине при первой сборке нужен доступ к github.com.
  Вместе с пакетом подтянулись 13 служебных пакетов сборки (`hooks`, `code_assets`,
  `native_toolchain_c`, `ffi` и др.). Вторая половина проверки (шаг 2.2, 2026-09-20): `NativeDatabase.memory()` из
  drift 2.35.0 открывается и выполняет запросы в `flutter test` на Windows (запрос, запрос с
  параметром, создание таблицы, вставка и чтение). Вопрос закрыт; остаётся проверка на iOS (этап 3).
- **Риск, который надо проверить на первом же шаге с БД:** запустится ли
  `NativeDatabase.memory()` в `flutter test` на Windows без ручной установки `sqlite3.dll`.
  По описанию `sqlite3` 3.x должен бундлиться автоматически, но в документации drift по
  тестированию это явно не написано — проверяем практикой, и если нет, добавляем DLL в
  инструкцию по настройке машины (не в зависимости приложения).

### Задел под будущую синхронизацию двух пользователей

Синхронизацию сейчас **не делаем** и не проектируем. Но выбор drift ей не мешает, а схема
подготовлена так, чтобы дверь осталась открытой:

- UUID вместо автоинкремента → записи, созданные на двух телефонах, не столкнутся id.
- `updated_at` → можно будет сравнивать версии и разрешать конфликты «последний выиграл».
- `deleted_at` (мягкое удаление) → удаление тоже можно передать как изменение; без него
  удалённая на одном телефоне запись «воскресала» бы с другого.
- Когда (и если) дойдёт до синхронизации, добавится таблица журнала изменений и флаг
  «не отправлено». Это обычная миграция схемы, а drift такие миграции умеет и тестирует.

## Последствия

**Становится проще:**

- Запросы проверяются компилятором: опечатка в имени колонки — это ошибка сборки, а не
  падение на телефоне. Для новичка это главный выигрыш.
- Агрегаты (`SUM`, `GROUP BY`, `BETWEEN` по датам) пишутся либо на Dart-API, либо обычным SQL
  через `customSelect` — под аналитику этапа 4 хватит и того, и другого.
- Тесты слоя `data` идут на настоящей SQLite в памяти, без моков. Мокать базу не придётся.
- Реактивность: `watch()` отдаёт `Stream`, который сам обновляется после записи. Это
  закрывает «список операций обновился после добавления» без стейт-менеджера (см. 0002).

**Становится сложнее:**

- Появляется кодогенерация: `build_runner`, сгенерированные файлы `*.g.dart`, отдельный шаг
  «после правки таблиц — перегенерировать». Для новичка это новое понятие и новый источник
  непонятных ошибок («тип не найден» = забыл сгенерировать).
- Сгенерированные файлы придётся закоммитить (или каждый раз генерировать в CI) — надо
  один раз договориться и записать в `CLAUDE.md`.
- Четыре записи в `pubspec.yaml` вместо одной. Это осознанное отступление от «минимума
  зависимостей»: платим строчками в pubspec за безопасность запросов и за тесты.

**Риски для новичка и что с ними делать:**

| Риск | Насколько вероятно | Что делаем |
|---|---|---|
| Запутаться в кодогенерации | высоко | первый шаг с БД — минимальный: одна таблица, одна миграция, один тест |
| `NativeDatabase.memory()` не заведётся в тестах на Windows | средне | проверяем сразу на этапе 2, до того как напишем много кода |
| Нативная часть SQLite сломает облачную iOS-сборку | низко (sqlite3 3.x бундлится сам) | первую iOS-сборку (этап 3) делаем **сразу после** появления БД, чтобы узнать об этом рано |
| drift «умрёт» | низко (один автор, но 1.3 млн загрузок, релиз 9 дней назад) | под drift лежит обычный SQLite: схема и данные переносимы, при необходимости переписываются запросы, а не данные |
| Автор пакета — один человек | средне | принимаем: альтернатива (`sqflite`) тоже поддерживается одним издателем |

## Отвергнутые варианты

### `sqflite` (2.4.4, tekartik.com, 5560 лайков, 160 points, 3.13 млн загрузок, 8 дней назад)

Самый популярный способ работать с SQLite во Flutter, и он честно решает задачу. Отвергнут по
трём причинам, каждая из которых бьёт именно по новичку:

1. **Запросы — строки.** `db.rawQuery('SELECT ...')` возвращает `List<Map<String, Object?>>`,
   каждый маппинг в объект пишется руками. Опечатка в имени колонки или в типе всплывёт
   только в рантайме. При том объёме агрегатов, который нужен аналитике, это постоянный
   источник ошибок.
2. **Тесты.** `sqflite` — плагин на платформенных каналах, платформы на pub.dev: Android, iOS,
   macOS. В обычном `flutter test` на Windows он не работает — нужен ещё один пакет
   (`sqflite_common_ffi`) и отдельная инициализация в тестах. То есть «минимум зависимостей»
   на деле не соблюдается, зато тестовая и боевая конфигурации расходятся.
3. **Миграции руками.** `onUpgrade` с `switch` по версиям и без готовых инструментов проверки
   «схема после миграций совпадает со схемой с нуля».

Ради честности: у `sqflite` нет кодогенерации, и это его сильная сторона — меньше магии.
Если на этапе 2 drift окажется для новичка неподъёмным, `sqflite` — первый кандидат на замену.

### Пакет `sqlite3` напрямую (без drift)

Технически это то, на чём drift и стоит: FFI-биндинги, нативный SQLite в комплекте,
`sqlite3.openInMemory()` для тестов, полный контроль. Отвергнут: без генератора придётся
руками писать и маппинг строк в объекты, и весь механизм версионирования схемы, и
реактивные обновления списков. Это ровно та работа, которую drift уже сделал, и для новичка
она даст больше багов, чем понимания. Оставляем как «аварийный выход»: если drift
разонравится, слезть на `sqlite3` можно без миграции данных — файл базы тот же.

### Не-SQL хранилища (Hive / Isar / ObjectBox / JSON-файл)

Не рассматривались всерьёз и не подходят: нужны реляционные агрегаты по датам и категориям
(`GROUP BY`, `SUM`, диапазоны дат) — это ровно то, для чего существует SQL. Плюс `CLAUDE.md`
уже зафиксировал SQLite как рамку. JSON-файл отдельно плох тем, что при росте истории
операций его придётся целиком читать и целиком переписывать.

## Дополнение 2026-09-20: комментарий и подкатегории

- Статус дополнения: **принято пользователем 2026-09-20**. Шапка основного ADR (статус и дата
  2026-09-19) не меняется — решение про drift осталось тем же, здесь только уточняется схема.
- Это **заметка для этапа 2**, а не готовый SQL. Точные `CREATE TABLE`/`CREATE INDEX` пишутся
  в шаге реализации первой версии таблиц; здесь зафиксировано, какие колонки обязаны в ней быть.

### Контекст

2026-09-20 пользователь принял два решения по интерфейсу (подробности и его слова — в
`docs/ROADMAP.md`, раздел «Решения по интерфейсу (2026-09-20)»):

1. У операции есть **одно необязательное поле «Комментарий»** — строка над сеткой категорий на
   экране быстрого ввода. До 200 символов, пробелы по краям обрезаются, пусто = «нет
   комментария». Если её не трогать, путь «кнопка → число → категория» не меняется.
2. **Подкатегории с одним уровнем вложенности** (категория → подкатегория), необязательные,
   включаются пользователем для конкретной категории. При выборе категории с подкатегориями
   открывается их сетка, первой плиткой — «Пропустить». Круговая диаграмма на главном экране
   считает **только категории**; разбивка по подкатегориям — в разделе «Аналитика» (этап 4).
   Подкатегории работают и для доходов, и для расходов.

Оба решения меняют схему БД, а таблицы этапа 2 ещё не написаны. Пользователь согласился
заложить и то, и другое **сразу в первую версию схемы**, чтобы не делать лишнюю миграцию
почти пустой базы.

### Решение: что должно быть в схеме этапа 2

Поверх общих соглашений выше (`id`, `created_at`, `updated_at`, `deleted_at`).

**Таблица операций `transactions`:**

| Колонка | Тип | Что это |
|---|---|---|
| `note` | `TEXT` NULL | комментарий пользователя. `NULL` = комментария нет. До 200 символов, пробелы по краям обрезаются, пустая строка в базу **не пишется** — превращается в `NULL`. Длину и обрезку проверяет `domain` (и `maxLength` в поле ввода), **а с 2026-09-20 ещё и сама база**: `CHECK` разрешает либо `NULL`, либо строку длиной 1–200 символов (см. дополнение «Ужесточение схемы v1» ниже) |
| `category_id` | `TEXT` NOT NULL | **всегда категория верхнего уровня** (у неё `parent_id IS NULL`) |
| `subcategory_id` | `TEXT` NULL | подкатегория этой же категории или `NULL` («Пропустить» и случай, когда подкатегорий нет). `domain` проверяет согласованность: у выбранной подкатегории `parent_id == category_id` |

**Таблица категорий `categories`:**

| Колонка | Тип | Что это |
|---|---|---|
| `parent_id` | `TEXT` NULL | `NULL` = категория верхнего уровня, иначе ссылка на категорию верхнего уровня **того же вида** (доход/расход). Вложенность максимум 1 уровень: у подкатегории своих подкатегорий быть не может. Правило проверяет `domain`; база держит ссылочную целостность внешним ключом на `categories.id` |
| `sort_order` | `INTEGER` NOT NULL | порядок плиток в сетке, задаёт пользователь. Считается **внутри своего уровня**: у категорий верхнего уровня — между собой, у подкатегорий — внутри своего родителя. Хранится у самой категории, а не в общих настройках |
| `archived_at` | `INTEGER` NULL | архив вместо удаления. `NULL` = категория живая и видна в сетке. Категорию или подкатегорию, к которой уже привязаны операции, не удаляем, а архивируем: из сеток выбора она исчезает, старые операции и история остаются целыми |

**Индексы и агрегаты:**

- индексы под агрегаты по категориям: по `category_id` (вместе с колонкой локальной даты
  операции и условием `deleted_at IS NULL`) — на них опираются итоги и диаграмма;
- итоги по категориям (главный экран, диаграмма) считаются **прямо по `category_id`**, без
  join и без подкатегорий;
- разбивка по подкатегориям (детализация в «Аналитике», этап 4) считается по
  `subcategory_id` внутри одной категории.

**Что этим дополнением НЕ решается** (осталось на этап 2 и на отдельные решения):
подсказки по прошлым комментариям, поиск по комментарию в «Истории», колонки экспорта CSV,
иконки и цвета категорий, точный вид экрана управления подкатегориями.

### Последствия

**Становится проще:**

- Итоги и диаграмма по категориям — один `GROUP BY category_id`, без join и без «поднимания»
  подкатегории к родителю. Это самый частый запрос в приложении, и он остаётся дешёвым.
- Включить или выключить подкатегории для категории — это про строки в `categories`, таблицу
  операций трогать не надо. Операции без подкатегории просто держат `subcategory_id IS NULL`.
- Комментарий — одна нулевая колонка: `NULL` ничего не занимает и ничего не ломает в старых
  запросах.
- Архив (`archived_at`) отделён от мягкого удаления (`deleted_at`): «спрятать из сетки» и
  «удалить запись» — разные состояния, и одно не мешает другому.

**Становится сложнее:**

- У операции **две** ссылки на категории вместо одной, и их согласованность (`parent_id`
  подкатегории == `category_id` операции) база сама не проверит — это правило `domain`, и на
  него нужен тест. Если правило нарушить, аналитика покажет операцию в «чужой» категории.
- В `categories` лежат сущности двух смыслов (категории и подкатегории), значит почти каждая
  выборка должна явно писать `parent_id IS NULL` или `parent_id = ?`. Забыл условие — в сетке
  верхнего уровня появятся подкатегории.
- Правка операции в «Истории» должна уметь менять пару «категория + подкатегория» вместе: смена
  категории обязана сбрасывать подкатегорию.
- Фильтров в запросах стало больше: `deleted_at IS NULL` + `archived_at IS NULL` + уровень.

### Отвергнутые варианты

**1. Хранить в операции только одну ссылку — на лист дерева** (подкатегорию, если она есть,
иначе категорию). Меньше колонок, нет риска рассогласования. Отвергнуто: тогда **любой** итог
по категории требует join с `categories`, чтобы поднять подкатегорию к родителю. А итоги по
категориям — самый частый запрос (главный экран при каждом открытии), и его нельзя делать
дороже ради редкой детализации. Плюс вопрос «а это категория или подкатегория?» пришлось бы
решать при каждом чтении операции.

**2. Произвольная глубина вложенности** (дерево любой высоты через `parent_id`). Схема та же,
но агрегаты превращаются в рекурсивные запросы (`WITH RECURSIVE`), а UI — в навигацию по
уровням с «назад». Отвергнуто: пользователь прямо сказал «Один уровень вложенности, да», а
рекурсивные агрегаты для новичка — источник медленных и непонятных запросов. При этом дверь не
закрыта: колонка `parent_id` та же, ограничение «1 уровень» живёт в `domain`, а не в схеме.

**3. Комментарий как единственный способ помечать магазин** (без подкатегорий вообще: писать
«Пятёрочка» в текст). Соблазнительно — ноль новых сущностей. Отвергнуто: по свободному тексту
нельзя честно считать статистику («Пятёрочка», «пятерочка», «5ка» — три разные строки), а
пользователю пришлось бы печатать вместо одного касания. Комментарий остаётся для разового
пояснения («подарок маме»), подкатегория — для повторяющегося разреза, по которому считают
суммы.

**4. Отдельная таблица `subcategories`.** Своя таблица с полями `id`, `category_id`, `name`,
`sort_order`. Отвергнуто: почти полная копия `categories` (те же имя, иконка, порядок, архив,
те же экраны управления) и вдвое больше кода на, по сути, одну и ту же сущность. Одна таблица
с `parent_id` дешевле, а «1 уровень» всё равно проверяется в `domain`.

## Дополнение 2026-09-20: ужесточение схемы v1, каталог базы и резервное копирование

- Статус дополнения: **принято пользователем 2026-09-20** по итогам QA-ревью вехи 2A. Шапка
  основного ADR не меняется: выбор drift остался тем же, здесь уточняются схема и открытие базы.
- Реализуется шагом **2.9b** этапа 2 (см. `docs/ROADMAP.md`).

### Контекст

Веха 2A закрыта: таблицы `app_settings`, `categories`, `transactions` созданы, снимок схемы
версии 1 выгружен, файловая база открывается на устройстве. Блокирующих проблем ревью не нашло,
но нашло места, где база **разрешает** записать заведомо неверные данные. Пока приложение пишет
в неё только наш код, это не видно; но база — последний рубеж, и чинить её дешевле сейчас, пока
схема **ещё не выпущена** (приложения нет ни у кого, кроме разработчика, данных в нём нет).
После этапа 3 такие правки пойдут уже миграцией.

### Решение 1: база сама проверяет то, что можно проверить

Добавляем `CHECK`-ограничения и один индекс:

| Что | Ограничение | Зачем |
|---|---|---|
| `currency` | ровно три заглавные латинские буквы (проверка `GLOB`) | валюта — код ISO 4217 (`RUB`). Без проверки в базу можно записать «руб», «RUB », пустую строку — и `Money` при чтении бросит ошибку уже на экране |
| `occurred_on` | целое в диапазоне 10101..99991231 | это дата вида ГГГГММДД (ADR 0004). Проверка не даёт записать 0, отрицательное число или мусор. Она грубая (31 февраля пройдёт) — полную корректность даты держит `DateOnly` в коде, база ловит только явную чушь |
| `note` | `NULL` **или** строка длиной 1–200 символов | пустая строка и строка из пробелов — это «нет комментария», их превращает в `NULL` слой репозитория (правило `domain`), а база теперь физически не даёт записать пустой комментарий или длиннее 200 символов. Раньше здесь было написано «база тут ничего не сторожит» — это исправлено |
| индекс `(occurred_on, occurred_at)` | — | история показывает операции по дням, внутри дня — по времени. Без второго поля в индексе база сортирует каждый день заново |

Плюс классы строк таблиц переименованы в `TransactionRow` и `CategoryRow` (`@DataClassName`):
иначе сгенерированный drift класс `Transaction` столкнётся с доменной сущностью `Transaction`
из шага 2.12, и придётся везде писать `as`-импорты.

**Снимок схемы v1 перевыгружается заново.** Общее правило — выпущенный снимок править нельзя,
по нему проверяются миграции на устройствах пользователей. Здесь правило не нарушается: версия 1
ещё не выпущена. Это разовое исключение, и после этапа 3 оно больше не действует.

### Решение 2: тесты схемы — белый список типов и проверка планов запросов

- Сторож «в схеме нет столбцов типа `REAL`» (шаг 2.7) переворачивается на **белый список**:
  разрешены только `TEXT` и `INTEGER`. Чёрный список ловит только то, о чём мы подумали заранее;
  белый поймает и `REAL`, и `NUMERIC`, и `BLOB`, и опечатку в типе — сам, без нашего участия.
- Добавляются тесты `EXPLAIN QUERY PLAN` на три типовых запроса: операции за период; итог по
  категории за период; сетка живых категорий одного уровня. `EXPLAIN QUERY PLAN` — это команда
  SQLite «покажи, как ты собираешься выполнять запрос»; тест проверяет, что в плане есть имя
  нашего индекса, а не «перебор всей таблицы». Главная польза не в скорости: наши индексы
  частичные (с условием `deleted_at IS NULL`), и **запрос, в котором забыли `deleted_at IS NULL`,
  просто не попадёт в индекс** — тест это увидит и упадёт. То есть план запроса работает как
  сторож против забытого фильтра мягкого удаления.

### Решение 3: файл базы живёт в каталоге поддержки приложения

Файл базы переезжает из каталога документов (`getApplicationDocumentsDirectory`) в **каталог
поддержки приложения** (`getApplicationSupportDirectory`). Причина: на iOS «Документы» —
пользовательский каталог, который приложение может открыть для показа в системном «Файлах»;
служебному файлу базы там не место. Каталог поддержки — как раз для внутренних файлов
приложения, пользователю он не показывается. На Android разница невелика, но каталог один и тот
же в обоих системах — это проще.

Добавляются две проверки при открытии: тест «файл есть, но это не база» (подсунули посторонний
файл — получаем понятную ошибку, а не падение) и **защищённое закрытие соединения**: если
открытие сорвалось на полпути, соединение закрывается, а не остаётся висеть.

Как ошибка открытия выглядит для пользователя — решается отдельно, шагом 2.14a: `runApp`
вызывается всегда, при ошибке показывается экран «Не удалось открыть базу данных» с кнопкой
«Повторить».

**Переезд файла на существующих устройствах не нужен:** приложение ещё никому не установлено,
переносить нечего. Если бы оно было выпущено, потребовался бы разовый код переноса файла.

### Решение 4: Android Auto Backup отключаем, резервная копия — только CSV

В манифесте Android ставим `allowBackup="false"`. Android по умолчанию сам копирует данные
приложения (включая файл базы) в Google-аккаунт пользователя — это называется Auto Backup.
Решение пользователя 2026-09-20: «Отключаем Backup, оставляем только CSV».

Почему: это прямое следствие принципа local-first из `CLAUDE.md` — данные о тратах не уезжают
в облако без явного решения пользователя. Заодно снимается неприятный класс проблем: Auto Backup
копирует файл базы «как есть», в том числе в момент, когда SQLite не дописал журнал, и
восстановленная копия может оказаться повреждённой.

Цена решения: **переустановил приложение или потерял телефон — данные потеряны**, если нет
выгруженного CSV. Поэтому экспорт и импорт CSV (этап 6) становятся обязательной частью первой
версии, а не приятным дополнением. Это записано и в `docs/ROADMAP.md`.

### Последствия

**Становится проще:**

- Испорченные данные ловятся в момент записи, в тесте на машине разработчика, а не при чтении
  на телефоне пользователя.
- Белый список типов и тесты планов запросов работают сами: новый столбец неверного типа или
  запрос без `deleted_at IS NULL` уронят тест без того, чтобы кто-то об этом вспомнил.
- Одна причина «данные молча уехали в облако» исчезает совсем.

**Становится сложнее:**

- `CHECK`-ограничения возвращают ошибку базы, а не понятное сообщение. Репозитории (шаги 2.11 и
  2.13) обязаны превращать её в доменную ошибку — иначе пользователь увидит текст SQLite.
- Тесты `EXPLAIN QUERY PLAN` привязаны к именам индексов: переименовали индекс — поправьте тест.
  Это осознанная цена: такой тест и должен падать, когда индекс пропал.
- Пользователь остаётся без автоматической резервной копии до этапа 6. До тех пор единственная
  честная рекомендация — «не держите в приложении данные, которые жалко потерять».
