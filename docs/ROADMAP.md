# MoneyAPP — план и принятые решения

Обновляется по мере работы. Правила процесса — в `CLAUDE.md`, архитектурные решения — в `docs/decisions/`.

## Цель

Минималистичное, но глубокое по функциям приложение учёта доходов и расходов для Android и iOS. Сначала для себя (тесты на iPhone 14 Pro Max и на Android-телефоне), позже — публикация. Идеология: без назойливой рекламы, без «выкачивания денег»; в будущем платная подписка с дополнительными возможностями и возможность поддержать разработчика. Ориентир по удобству: Monefy (быстрый ввод), но с более сильной аналитикой и кастомизацией без подписки.

## Принятые решения (2026-09-19)

- **Local-first.** Все данные только на устройстве. Аккаунтов и синхронизации в первой версии нет.
- **Валюта:** только рубли. Код валюты хранится у каждой суммы (задел под мультивалютность).
- **Идентификаторы записей — UUID**, у записей есть `createdAt`/`updatedAt` и мягкое удаление (задел под будущий совместный бюджет).
- **Язык:** русский. **Темы:** светлая/тёмная, выбор в настройках.
- **Основной сценарий:** сделал покупку → ввёл цену → выбрал категорию (2–3 касания). Категории в подсказке упорядочиваются по частоте и времени суток (простая статистика, без ИИ).
- **Доходы и расходы** — отдельные наборы категорий. Категории по умолчанию + свои. Расходы — красная гамма, доходы — зелёная; смысл не должен передаваться только цветом (знак или иконка).
- **Баланс:** источники денег (Банк А, Наличные…). При первом запуске можно ввести текущие остатки (необязательно). Есть источник по умолчанию для расходов; остаток меняется от операций. Привязка операции к источнику необязательна, быстрый ввод остаётся «цена → категория».
- **Регулярные платежи:** календарь плановых платежей; в нужный день локальное уведомление и отметка в списке напоминаний (оплатил / пропустить / убрать). Заложить ограничения локальных уведомлений (около 64 запланированных на iOS, энергосбережение на Android).
- **Экспорт и импорт CSV** входят в первую версию (защита от потери данных при потере телефона).
- **Аналитика:** итоги за день/неделю/месяц/год/свой интервал, круговая диаграмма по категориям.
- **iOS без Mac:** разработка на Android (эмулятор, потом телефон); iOS-сборки в облаке (Codemagic или GitHub Actions на macOS). Распространение через TestFlight, если удастся оформить Apple Developer Program; иначе запасной путь — бесплатная установка своим Apple ID (7 дней, ограничения). Android-тестировщику отправляем APK.
- **Идентификатор приложения:** `com.tonyvinsenty.zuno` *(изменён 2026-09-20; ранее был `com.tonyvinsenty.moneyapp`)*, имя пакета Dart: `money_app`.

Слова пользователя: «Доход это кнопка "+", расход это кнопка "-" на главном экране с агрегированной круговой диаграммой расходов за текущий минус. То есть эта кнопка -> число -> категория». Над сеткой — отдельная строка «умной подсказки» (частота использования и время суток); подсказка порядок самой сетки не меняет. Слова пользователя: «Стабильная сетка (иконки с названиями в строках и столбцах). Порядок задается пользователем в Настройках. Умная подсказка над сеткой».

Слова пользователя: «Редактирование из вкладки "История". Просто нажать на строку с доходом/расходом, там же можно изменить сумму/дату/категорию, или удалить событие». Состав полей дополнен решениями от 2026-09-20 (комментарий и подкатегория — в «мелких правилах» ниже, тип операции — в разделе по итогам ревью этапа 1).
- **Вкладка «Аналитика» остаётся отдельной.** Итоги за день/неделю/месяц/год/свой интервал и диаграмма по категориям живут там; главный экран показывает только диаграмму расходов за текущий месяц. Слова пользователя: «Да, вкладка Аналитика нужна».
- **Правила удаления: отмена и архив.** Слова пользователя: «Да и Да». Значит:
  - операция удаляется сразу, но внизу экрана появляется `SnackBar` с кнопкой «Отменить» (живёт примерно 5–6 секунд). Удаление **мягкое** (запись помечается удалённой, а не стирается), поэтому отмена дешёвая. Диалога «Вы уверены?» нет;

Менять сейчас безопасно: приложение не опубликовано, а после публикации идентификатор уже не изменить. **Не меняются**: имя Dart-пакета `money_app` и название репозитория `MoneyAPP`.
- **Пакет `intl` согласован для шага 1.4.** Слова пользователя: «Согласен на добавление пакета для 1.4». Согласие получено 2026-09-20.
- **Комментарий к операции — одно необязательное поле.** У каждой операции (дохода и расхода) есть текстовое поле «Комментарий». На экране выбора категории сверху стоит узкая строка «Комментарий (необязательно)». Если её не трогать, тап по категории сразу сохраняет операцию — привычный путь «кнопка → число → категория» остаётся в те же 3 действия. Если комментарий введён и нажата категория (или подкатегория), сохраняется всё вместе. Клавиатура открывается **только** по тапу на эту строку, сама не выскакивает. Длина — до 200 символов, пробелы по краям обрезаются, пустая строка = «нет комментария» (в БД `NULL`). Пользователь согласился на это предложение 2026-09-20. **Позже, не сейчас:** подсказки по прошлым комментариям и поиск по комментарию во вкладке «История»; комментарий попадает в экспорт CSV.
- **Подкатегории — один уровень вложенности.** Слова пользователя: «Один уровень вложенности, да. Кнопка Пропустить для подкатегорий первой. На диаграмме учитываем только Категории. Подобную агрегацию уже делать в разделе Аналитика». Значит:
  - дерево ровно на два уровня: категория → подкатегория. Подкатегория своих подкатегорий иметь не может;
  - подкатегории необязательны: пользователь сам включает их для нужной категории в «Настройках» (там же, где порядок категорий);
  - если у выбранной категории есть подкатегории, после тапа по ней открывается сетка подкатегорий, **первой плиткой — «Пропустить»** (сохранить операцию только с категорией). Уже введённый комментарий при переходе на эту сетку не теряется;
  - круговая диаграмма на главном экране считает **только категории**, подкатегории в ней не видны;
  - разбивка по подкатегориям живёт в разделе «Аналитика» (этап 4) — например, по нажатию на сектор или строку категории;
  - подкатегории работают и для доходов, и для расходов.
- **Умная подсказка может предлагать пару «Категория · Подкатегория».** Строка подсказки над сеткой (решение про подсказку принято выше) вправе показывать готовую пару, например «Продукты · Пятёрочка», и сохранять операцию одним касанием. Так путь «кнопка → число → подсказка» остаётся в 3 действия даже с подкатегориями. Ответ пользователя: «Да».
- **Мелкие правила комментария и подкатегорий (решено 2026-09-20).** Ответы пользователя: «Да, можно менять» / «Без галочки» / «Согласен с рекомендацией» / «В первой версии нельзя». Значит: (а) в «Истории» при правке операции можно менять **комментарий и подкатегорию** (при смене категории подкатегория сбрасывается); (б) отдельной галочки «Включить подкатегории» нет: подкатегории есть у той категории, у которой добавлена хотя бы одна, сетка подкатегорий появляется сама; (в) если у категории все подкатегории в архиве, сетка подкатегорий не показывается, тап по категории сохраняет операцию сразу; (г) в первой версии подкатегорию нельзя переносить в другую категорию и нельзя превращать категорию в подкатегорию (и наоборот), чтобы не переписывать сохранённые операции.
- **Порядок реализации подкатегорий и комментария.** Предложение architect, с которым пользователь согласился: и комментарий, и подкатегории закладываются в схему БД **сразу**, в первой версии таблиц этапа 2 (чтобы не делать лишнюю миграцию). Комментарий появляется уже в первом экране быстрого ввода. Экран подкатегорий (сетка с «Пропустить», включение и правка подкатегорий в настройках категорий) — **отдельный шаг этапа 2 после** того, как базовый сценарий «кнопка → число → категория» заработал.

Ниже — решения, принятые по итогам ревью этапа 1 (2026-09-20). На каждое предложение ревью пользователь ответил «Да».

- **Дата при быстром вводе — плашка «Сегодня».** Рядом с полем суммы стоит маленькая плашка с текущей датой (обычно на ней написано «Сегодня»). Тап по ней открывает календарь и позволяет поставить вчерашний или любой другой день. В обычном случае плашку трогать не нужно, поэтому быстрый ввод остаётся в те же 3 действия: кнопка → число → категория. Раньше дату можно было изменить только потом, в «Истории»; теперь — сразу, но без лишних касаний.
- **Отмена сразу после сохранения.** После того как операция сохранена, внизу экрана появляется сообщение вида «Расход 350 ₽ · Продукты сохранён» с кнопкой «Отменить» (живёт примерно 5–6 секунд). «Отменить» — это мягкое удаление только что созданной записи, тем же механизмом, что и отмена удаления в «Истории». Правило действует и для сохранения **одним касанием по умной подсказке**: именно там легче всего промахнуться, поэтому путь назад нужен обязательно. Диалогов подтверждения по-прежнему нет.
- **Тип операции можно менять в правке.** В «Истории» при правке операции разрешено переключить доход ↔ расход. **При смене типа категория и подкатегория сбрасываются**: у доходов и расходов разные наборы категорий, поэтому старый выбор просто некуда перенести — пользователь выбирает категорию заново. На экране ввода тип виден **сразу тремя способами**: заголовок словом («Новый расход» / «Новый доход»), цвет и знак («−» / «+»). Одним цветом смысл не передаётся — это общее правило приложения.
- **Кнопки «+» и «−» на главном экране подписаны словами.** Рядом со знаком (или под ним) стоят подписи «Доход» и «Расход», чтобы не гадать, какая кнопка что делает. Для скринридера у кнопок свои подписи — «Добавить доход» и «Добавить расход» (через `Semantics`, это «ярлык для озвучки», видимый текст от него не меняется). Зона нажатия каждой кнопки — **не меньше 48×48 dp** (минимум, рекомендованный и Android, и iOS).
- **Нулевая сумма остаётся допустимой.** Ревью предлагало запретить ввод «0», но прежнее решение пользователя в силе: ноль можно сохранить и как доход, и как расход (на баланс не влияет, годится как пометка). Экран быстрого ввода этапа 2 **не должен** показывать ошибку на ноль.

- **Тексты ошибок ввода суммы утверждены.** Слова пользователя: «Тексты ок». Окончательные формулировки (живут в `lib/core/ui/amount_failure_text.dart`, по одной на причину отказа):
  - `empty` — «Введите сумму»;
  - `notANumber` — «Введите сумму цифрами. Пример: 1 234,56»;
  - `negative` — «Знак не нужен: доход это или расход, зависит от нажатой кнопки»;
  - `tooManyDecimals` — «После запятой или точки — не больше двух цифр. Тысячи пишите без точки: 1234»;
  - `tooManySeparators` — «Слишком много запятых или точек. Пример: 1 234,56»;
  - `tooLarge` — «Слишком большая сумма (не больше 1 000 000 000 000 ₽)».

  Пример суммы и предел подставляются в текст из кода форматирования, а не набираются руками, поэтому в приложении разделитель разрядов всегда один и тот же. Формулировки больше не «уточняются»: они приняты и меняются только новым решением пользователя.
- **Набор категорий по умолчанию утверждён.** Слова пользователя: «Предложенный набор категорий — Ок». При первом запуске создаются:

  - **доходы** (4): Зарплата, Подработка, Подарок, Прочее.

  Порядок в списке — это и есть порядок плиток в сетке при первом запуске. Иконки — из стандартного набора Material Icons, конкретные подбираются при реализации. Список потом правится пользователем в «Настройках» (переименовать, добавить свои, отправить в архив, поменять порядок).

**Требования к этапу 2: комментарий и подкатегории (решено 2026-09-20).** Порядок работ внутри этапа 2 фиксирован:

1. **Схема БД сразу поддерживает и комментарий, и подкатегории** — они попадают в первую версию таблиц, чтобы потом не делать отдельную миграцию. Заметка по колонкам — в дополнении к [ADR 0001](decisions/0001-local-storage-drift.md) от 2026-09-20.
2. **Комментарий входит в первый же экран быстрого ввода:** узкая строка «Комментарий (необязательно)» над сеткой категорий, до 200 символов, пробелы по краям обрезаются, пусто = `NULL`, клавиатура только по тапу. Тап по категории при пустой строке сохраняет операцию сразу — базовый сценарий не удлиняется.
3. **Подкатегории — отдельный шаг после базового сценария:** сетка подкатегорий с плиткой «Пропустить» первой, включение и правка подкатегорий в настройках категорий, сохранение введённого комментария при переходе на сетку. Вложенность строго один уровень, проверку «у подкатегории нет своих подкатегорий» делает `domain`.
4. **Диаграмма на главном экране считает только категории.** Разбивка по подкатегориям — этап 4 («Аналитика»).

### Требования к этапу 2 из ревью этапа 1 (2026-09-20)

Это **не** решения пользователя, а список того, что `architect` обязан проработать при проектировании экранов этапа 2, а `flutter-developer` — не потерять. Собрано по итогам ревью QA и UX.

**Поле ввода суммы**

- Фильтр ввода: принимаются только цифры, пробелы, запятая и точка; всё лишнее **молча не печатается** (никаких ругательных сообщений на каждую букву).
- На iOS у числовой клавиатуры нет кнопки «Готово» — нужна видимая кнопка «Далее» над клавиатурой, иначе её нечем закрыть.
- Третью цифру после запятой просто **не дать напечатать** (лучше, чем показать ошибку после ввода).
- Группировка разрядов прямо во время печати («12 345,6») и обязательная проверка, что курсор не прыгает в начало строки при вставке пробелов.
- Ошибка — текстом **под полем** (`errorText`), а не всплывающим сообщением. Текст «Введите сумму» не показываем, пока человек не попытался сохранить хотя бы раз.
- Сумма при вводе — крупным шрифтом: это главный элемент экрана.
- Для скринридера сумма читается словами: «Расход 1234 рубля 50 копеек», а не «минус 1234 запятая 5».
- Большие суммы при крупном системном шрифте не должны «ломать» верстку — обернуть в `FittedBox` (виджет, который ужимает содержимое под доступную ширину).

**Комментарий**

- Подпись «необязательно» видна **постоянно**, а не только пока поле пустое.
- Счётчик символов до 200.
- Подсказка пользователю, что тап по категории сохраняет операцию сразу вместе с введённым комментарием.

**Первый запуск**

- Набор категорий по умолчанию с иконками — **решено 2026-09-20**, состав см. в «Решениях по интерфейсу» выше (10 расходных, 4 доходных). Осталось подобрать иконки при реализации.

### Уточнения к критериям

**Правило чистоты `core` (шаг 1.6a).** Файлы в `lib/core/money`, `lib/core/time`, `lib/core/id` — это `domain`-код по смыслу, даже если лежат не в папке `domain`. В них **нельзя** `import 'package:flutter/...'`, `package:drift/...`, `package:intl/...` и **нельзя** слово `double`. Проверяет это маленький тест-сторож (`test/core/core_purity_test.dart`): читает `.dart`-файлы из этих трёх папок и падает, если находит запрещённое. Папки, которых ещё нет, тест пропускает — поэтому он появляется один раз на шаге 1.6a и автоматически охраняет файлы, добавленные на шагах 1.7, 1.8 и 1.10.

**Шаг 1.6 — `Money`.** Юнит-тесты обязательно покрывают:

- ноль, отрицательные значения (они разрешены: остаток по источнику, «доходы минус расходы»);
- **разные валюты — ошибка:** `RUB + USD` и `RUB - USD` бросают `ArgumentError`; `compareTo` для разных валют — тоже `ArgumentError` (молча сравнивать копейки нельзя);
- `allocate(0)` и `allocate(отрицательное число частей)` — ошибка;
- сумма частей `allocate` равна исходной сумме для 1, 3, 7 частей;
- `allocate` **отрицательной** суммы: части тоже отрицательные и их сумма равна исходной (копейка не теряется и в минусе);
- деление с округлением половины от нуля: делитель **должен быть положительным**: при `<= 0` бросается `ArgumentError` (не `assert`, чтобы защита работала и в релизной сборке); деление на ноль — ошибка;
- «большие значения»: в Dart переполнение `int` **происходит молча** (без исключения), поэтому тест не ждёт ошибки, а фиксирует осознанную границу — до какой суммы тип работает честно. Это тест-документация: если кто-то потом решит проверять переполнение, он увидит текущее поведение.

**Шаг 1.7 — `parseAmount` (выполнен, решения пользователя 2026-09-20).** Результат — sealed-тип `AmountParsed(Money)` / `AmountParseFailed(причина)`. Разбираются: «1 234,56» с обычным, неразрывным (U+00A0) и узким неразрывным (U+202F) пробелом, «1234.5», «,5», «5,», «00012,3» (=12,30), «0» (**ноль допустим** как доход и расход). Ошибки: «» и пробелы (`empty`); «abc», «+5», «5 ₽», «1e5» (`notANumber`); «-100» и «−100» (`negative`: направление задаёт тип операции); «1,2,3», «1,234,567», «1.234,56» (`tooManySeparators`); больше двух знаков после разделителя, включая «1.234» (`tooManyDecimals`, лишнее **не отбрасываем молча**); сумма больше **1 000 000 000 000 ₽** включительно (`tooLarge`, без переполнения: целая часть считается в BigInt). Тексты ошибок — в одном месте, `lib/core/ui/amount_failure_text.dart`. Обратный тест `parseAmount(format(x)) == x` — в шаге 1.9.

Плюс поведение поля ввода: на ошибку пользователь видит понятный человеческий текст, а не имя исключения. Причин отказа **шесть**: `empty`, `notANumber`, `negative`, `tooManyDecimals`, `tooManySeparators`, `tooLarge`. **Ноль ошибкой не считается** — он допустим. Тексты лежат в `lib/core/ui/amount_failure_text.dart`, по одному на причину; формулировки **утверждены пользователем 2026-09-20** («Тексты ок») и приведены в «Решениях по интерфейсу» выше.

**Шаг 1.8 — `DateOnly`, `Clock`, периоды.** Тесты с фиксированным `Clock`: границы недели/месяца/года, февраль и 29 февраля, свой интервал. Отдельно:

- **первый день недели — понедельник по умолчанию** (тест на это) и **один тест на воскресенье** как на настройку — чтобы параметр действительно был параметром, а не константой;
- **границы дней включительно** (`[первый день, последний день]`): «свой интервал» с 1 по 30 сентября включает и 1-е, и 30-е;
- **границы моментов — полуинтервал** `[начало периода, начало следующего периода)`: покупка в 23:59:59.999 последнего дня попадает в период, а первая миллисекунда следующего — уже нет.

**Шаг 1.10 — `uuid` v7.** Проверяем всегда: формат строки (36 символов, дефисы на своих местах), **версия 7** и **вариант** (нужные биты). Про возрастание: **Итог (2026-09-20):** пакет `uuid` 4.6.0 не гарантирует порядок внутри одной миллисекунды (после времени идут только случайные биты, счётчика нет), поэтому тесты проверяют возрастание лишь для id из разных миллисекунд, а внутри одной — уникальность. Практическое правило для этапов 2 и 6: если нужен строгий порядок создания внутри одной миллисекунды (например, пачка записей при импорте CSV), опираться на id нельзя — нужен `createdAt` плюс отдельный ключ порядка.

- тест «id возрастают» ставим **только** на id, созданные с **разным** «сейчас» (подставные часы: сгенерировали, сдвинули время, сгенерировали — второй id строго больше первого при сравнении строк);
- что происходит **внутри одной миллисекунды**, зависит от реализации пакета: гарантируется ли монотонность и как заполняются случайные биты. Сначала читаем документацию `uuid` на pub.dev, и только потом пишем тест ровно на то, что пакет обещает. Гадать и «закреплять» случайное поведение нельзя — такой тест начнёт падать после обновления пакета.

## Этап 2 — шаги

План составлен 2026-09-20 по решениям выше и ADR [0001](decisions/0001-local-storage-drift.md)–[0004](decisions/0004-money-dates-recurring.md). **Новых архитектурных решений этап 2 не требует:** все пять пакетов уже обоснованы в [ADR 0003](decisions/0003-dependencies.md), схема — в дополнении к ADR 0001, состояние и структура — в ADR 0002. Поэтому отдельного ADR 0005 на этот этап нет.

**Общий критерий каждого шага** (тот же, что на этапе 1): `dart format` ничего не меняет, `flutter analyze` чист, `flutter test` зелёный, для нового поведения есть тест, затем чекпоинт. Все шаги выполняет `flutter-developer` по одному.

**Ревью — на границах вех, а не после каждого шага.** После последнего шага каждой вехи: `/review-team` (QA + UX), затем сборка и **показ пользователю на эмуляторе**. Так ревью видит законченный кусок, а не полуфабрикат.

**Про пакеты.** Добавляются пять штук, по одному на шаг, каждый — **с явным согласием пользователя** и отдельным чекпоинтом: `sqlite3` (2.1), `drift` (2.2), `drift_dev` (2.3, только для разработки), `build_runner` (2.4, только для разработки), `path_provider` (2.9). Перед каждым таким шагом **возможно, потребуется выключить VPN**: загрузки с серверов Google медленные, а первая сборка с новым нативным пакетом тянет данные именно оттуда. Пакеты с pub.dev через VPN раньше скачивались нормально, так что тормозить будет скорее сборка под Android, чем `flutter pub get`.

**Про размер шагов.** Ограничение «до ~200 строк диффа» считается по коду, который пишет человек. Сгенерированные drift-файлы (`*.g.dart`) в счёт не идут: их не читают и не правят, но **коммитят** (ADR 0001).

### Что этап 2 намеренно не делает

- **Круговая диаграмма расходов на главном экране — предлагаю перенести в этап 4** («Аналитика»). Причины: (1) [ADR 0003](decisions/0003-dependencies.md) прямо откладывает решение «своя диаграмма на `CustomPainter` или пакет `fl_chart`» на начало этапа 4 — начав её в этапе 2, пришлось бы принимать это решение раньше срока; (2) диаграмме нужны итоги по категориям, то есть фича `analytics`, которой в этапе 2 ещё нет; (3) это плюс 2–3 шага к и без того длинному этапу. Вместо неё главный экран показывает итог расходов за месяц (шаг 2.26) — он тоже даёт мгновенную обратную связь «операция сохранилась», а место под диаграмму зарезервировано. Решение пользователя «на главном экране есть диаграмма» этим не отменяется, только переносится по срокам — см. вопрос 2 ниже.
- **Умная подсказка над сеткой категорий — предлагаю перенести в этап 6.** Подсказка опирается на статистику «частота плюс время суток», а статистики к концу этапа 2 ещё нет: она накопится, пока приложение используется после этапа 3. В роадмапе подсказки категорий и так стоят на этапе 6. Место над сеткой резервируется на шаге 2.23 — см. вопрос 3 ниже.
- **Источники денег (`accounts`), регулярные платежи, экспорт CSV, аналитика по подкатегориям** — этапы 4, 5 и 6. В схеме версии 1 их колонок нет намеренно: добавить `account_id` и ссылку на плановый платёж — это обычная миграция, механизм которой мы проверяем заранее на шаге 2.8.
- **Цвет у категории** в схему версии 1 не закладываем: для диаграммы этапа 4 цвета берутся из палитры темы по порядку категории. Если пользователь захочет свой цвет, это одна необязательная колонка и одна миграция.
- **Поиск по комментарию и подсказки по прошлым комментариям** — отложено решением пользователя от 2026-09-20.

### Этап 2 — вопросы к пользователю

Пять вопросов. Без ответов на первый начинать шаги 2.1–2.4 и 2.9 нельзя (правило `CLAUDE.md`: новый пакет — только с явным согласием).

1. **Согласны ли вы добавить пять пакетов этапа 2?** Это `sqlite3` (движок базы), `drift` (сама работа с базой), `drift_dev` и `build_runner` (генерация кода, только при разработке), `path_provider` (узнать, куда на телефоне класть файл базы). Все пять уже обоснованы в ADR 0003, версии на pub.dev проверены 2026-09-20 и с 19-го не изменились: drift 2.35.0, sqlite3 3.6.0 (нативный SQLite поставляется внутри пакета, отдельная DLL не нужна), drift_dev 2.35.0, build_runner 2.16.1, path_provider 2.1.6. Каждый добавляется отдельным шагом с чекпоинтом. **Подвопрос:** объединить ли шаги 2.3 и 2.4 (`drift_dev` и `build_runner`) в один? *Моя рекомендация: согласиться на все пять и объединить 2.3 с 2.4 — эти два пакета работают только в паре, в приложение не попадают и на сборку под iOS не влияют.*
2. **Переносим ли круговую диаграмму с главного экрана в этап 4?** В этапе 2 на главном тогда будут кнопки «+»/«−» и строка «Расходы за сентябрь: 12 345 ₽» плюс пустое состояние. *Моя рекомендация: да, переносить.* Причины — в разделе «Что этап 2 намеренно не делает». Ваше решение «на главном есть диаграмма» при этом остаётся в силе, меняется только срок.
3. **Переносим ли умную подсказку над сеткой категорий в этап 6?** Ей нужна накопленная статистика использования, которой к концу этапа 2 ещё нет. *Моя рекомендация: да, переносить; место над сеткой зарезервируем сразу.*
4. **Делать ли шаг 2.35 (тема сохраняется между запусками) в этапе 2 или подождать этапа 6?** Сейчас выбор темы живёт только в памяти и сбрасывается при перезапуске. *Моя рекомендация: сделать в этапе 2 — это один короткий шаг, а таблица настроек всё равно появляется на шаге 2.4.*
5. **Иконки категорий: подойдёт ли фиксированный набор примерно из 30 стандартных Material-иконок**, из которого вы выбираете иконку при создании категории? Свои картинки загружать нельзя, набор при желании расширяется позже одним шагом. *Моя рекомендация: да; это заодно избавляет от проблемы с пропадающими иконками в релизной сборке.*

## Отложено (идеи, пока не реализуем)

- **Совместный бюджет** по приглашению (синхронизация между двумя пользователями): потребует серверной части; модель данных к этому готовим заранее.
- **Мультивалютность** с конвертацией по актуальному курсу.
- **Подписка** с дополнительными возможностями и «поддержать разработчика». Условия Apple/выплаты придётся выяснять отдельно.
- **Чтение банковских уведомлений:** возможно только на Android, на iOS запрещено системой; надёжнее импорт выписок (CSV/Excel).
- **Распознавание чеков:** самый дешёвый вариант — сканирование QR-кода на чеке (сумма и дата, локально); остальное — позже и, возможно, не нужно.
