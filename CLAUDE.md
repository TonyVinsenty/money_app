# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Проект

MoneyAPP — мобильное приложение для учёта личных расходов (Flutter, Android + iOS). Проект только начинается: на этом этапе настроен процесс разработки, кода приложения ещё нет (нет `pubspec.yaml`, `lib/`, `test/`).

Общение с пользователем — на русском языке. Код, имена идентификаторов и сообщения коммитов — на английском, комментарии в коде — на русском только если это действительно нужно для понимания.

## Границы работы

- Работай **только внутри каталога проекта** `D:\Projects\Claude\MoneyAPP`, если пользователь явно не разрешил иное.
- **Не читай, не изменяй и не изучай** соседние проекты и файлы в `D:\Projects` (всё, что лежит вне каталога MoneyAPP): ни поиском, ни просмотром, ни «для примера».
- Считай соседние проекты **полностью изолированными и не связанными** с MoneyAPP: их код, зависимости, конфигурация и соглашения к этому проекту не относятся, ничего оттуда не заимствуй.
- Если в контекст попало описание соседних проектов (например, из файла `CLAUDE.md` выше по дереву каталогов), игнорируй его.
- Это правило действует и для субагентов и участников команды: указывай его в задаче, если передаёшь работу другому агенту.

## Принципы (обязательны для всех агентов)

1. **Разработчик — новичок.** Объясняй, что и зачем делаешь, простыми словами; новые термины Flutter/Dart расшифровывай один раз. Не выполняй большие «магические» переделки без согласования.
2. **Маленькие инкрементальные изменения.** Один шаг = одна проверяемая вещь (примерно до 200 строк диффа). Приложение должно собираться и проходить тесты после каждого шага.
3. **Local-first.** Источник истины — локальная база на устройстве. Приложение полностью работает без сети и без аккаунта. Никакого бэкенда, аналитики и облачных SDK, пока пользователь явно не решит иначе. Экспорт/резервное копирование — отдельная будущая задача, но модель данных не должна ей мешать (стабильные id, `createdAt`/`updatedAt`, мягкое удаление там, где это нужно).
4. **Деньги — никогда `double`.** Суммы хранятся целым числом в минорных единицах (копейки/центы) плюс код валюты. Форматирование — только на границе UI.
5. **Минимум зависимостей.** Сначала стандартная библиотека Dart и Flutter SDK. Любой новый пакет из `pubspec.yaml` требует письменного обоснования (ADR в `docs/decisions/`) и явного согласия пользователя. Команды `flutter pub add/remove/upgrade` намеренно требуют подтверждения.
6. **Тщательное тестирование.** Логика без теста не считается готовой (см. «Проверки»).
7. **Контрольные точки в Git.** После каждого зелёного шага — коммит-чекпоинт (`/checkpoint`). Никогда не переписывай историю и не делай `push` без прямой просьбы.

## Архитектурные ориентиры

Стек и ключевые решения приняты в ADR `docs/decisions/0001`–`0004` (2026-09-19). Перед работой над хранилищем, состоянием, пакетами, деньгами, датами или регулярными платежами прочитай соответствующий ADR; план и этапы — в `docs/ROADMAP.md`. Кратко:

- Слои: `domain` (чистый Dart, без Flutter-импортов: сущности, правила, репозиторные интерфейсы) → `data` (локальная БД, реализации репозиториев) → `presentation` (экраны, виджеты, состояние). Зависимости идут только внутрь, к `domain`. Фича не импортирует чужие `data`/`presentation`, только чужой `domain` (ADR 0002).
- Управление состоянием: встроенные средства Flutter (`ValueNotifier`/`ChangeNotifier`/`ListenableBuilder`, поток из базы через `StreamBuilder`). Пересмотр только через новый ADR (ADR 0002).
- Хранилище: SQLite через `drift` (ADR 0001). Схема версионируется, для каждой миграции есть тест. Сгенерированные файлы `*.g.dart` **коммитим**; после правки таблиц запускай генерацию (`dart run build_runner build`).
- Структура кода — по возможностям (feature-first): `lib/features/<feature>/{domain,data,presentation}`; общее — в `lib/core/`.
- Пакеты: только из списка ADR 0003, по одному на шаг, каждый с чекпоинтом. Всё, чего в списке нет, — только через новый ADR и согласие пользователя.
- Деньги, даты, регулярные платежи — по ADR 0004: `Money` = целые копейки + код валюты, сумма положительная, направление в поле «доход/расход»; дата операции хранится и как локальный день, и как момент UTC; «сейчас» берётся через `Clock`; неделя с понедельника; будущие операции заранее не создаются.

## Команды

Flutter SDK на этой машине пока **не установлен** (проверено 2026-09-19). Установка Flutter/Android Studio — отдельный первый шаг. Учтите: **собрать iOS-версию можно только на macOS с Xcode**; на Windows разрабатываем и тестируем на Android/эмуляторе, а код держим платформенно-нейтральным.

Корень репозитория = корень Flutter-приложения (без вложенной папки). Первичное создание проекта (когда дойдёт очередь; имя папки `MoneyAPP` не подходит как имя пакета из-за заглавных букв):

```powershell
flutter create --project-name money_app --platforms=android,ios .
```

После создания проверить, что `.gitignore` не потерял записи из уже существующего.

Ежедневные команды:

```powershell
flutter pub get                 # подтянуть зависимости
dart format .                   # форматирование
flutter analyze                 # статический анализ (должен быть без замечаний)
flutter test                    # все тесты
flutter test test/path/to_test.dart                  # один файл
flutter test --plain-name "часть названия теста"     # один тест по имени
flutter run                     # запуск на подключённом устройстве/эмуляторе
```

## Проверки («готово» означает)

Шаг завершён только если одновременно: `dart format` не меняет файлы, `flutter analyze` чист, `flutter test` зелёный, и для нового поведения есть тест. Что тестируем:

- `domain` и работа с деньгами — юнит-тесты (граничные случаи: 0, отрицательные, округление, разные валюты);
- `data` — тесты репозиториев на in-memory/временной БД, тесты миграций;
- экраны — widget-тесты ключевых сценариев (добавить/изменить/удалить расход, пустое состояние, ошибка ввода);
- `integration_test` — только для сквозных сценариев, когда базовые слои готовы.

## Рабочий процесс с агентами

Роли описаны в `.claude/agents/` и работают и как обычные субагенты, и как участники **команды агентов** (agent teams, экспериментальная функция — включена в `.claude/settings.json` через `CLAUDE_CODE_EXPERIMENTAL_AGENT_TEAMS=1`).

| Агент | Модель | Задача | Права |
|---|---|---|---|
| `architect` | opus | Дизайн, декомпозиция на маленькие шаги, ADR | читает всё; пишет только в `docs/` |
| `flutter-developer` | sonnet | Реализует один согласованный шаг вместе с тестами | читает/пишет код, запускает Flutter/Dart |
| `qa-reviewer` | opus | Проверяет корректность, тесты, граничные случаи, соблюдение принципов; запускает тесты | только читает; запускает команды |
| `ux-reviewer` | sonnet | Проверяет UX, доступность, тексты, поток добавления расхода | только читает |

Стандартный цикл на одну функцию:

1. **План.** `architect` разбивает задачу на шаги и описывает критерии готовности. Пользователь утверждает план.
2. **Реализация.** `flutter-developer` делает **один** шаг (тест → код → `analyze`/`test`).
3. **Ревью.** `/review-team` — `qa-reviewer` и `ux-reviewer` параллельно как команда. Замечания сводятся в один список.
4. **Исправление.** `flutter-developer` правит блокирующие замечания.
5. **Чекпоинт.** `/checkpoint <описание>` — проверки + коммит.

Правила для команд агентов:

- Писать код в один момент времени должен только один агент (`flutter-developer`): два агента, правящие один файл, затирают работу друг друга. Ревьюеры не правят код.
- Для параллельной работы дели задачи по **разным файлам**. Начинай с ревью и исследований — это самое безопасное применение.
- Команда расходует заметно больше токенов, чем одна сессия: для мелких правок используй обычную сессию или одного субагента.
- Итоги команды всегда сводит ведущая сессия и показывает пользователю до передачи разработчику.
- Если нужно отключить автоматическое превращение именованных субагентов в участников команды, поставь `CLAUDE_CODE_EXPERIMENTAL_AGENT_TEAMS` в `"0"` в `.claude/settings.json`.

## Навыки проекта

- `/checkpoint <описание>` — форматирование, анализ, тесты, затем коммит-чекпоинт (без `push`).
- `/review-team [область]` — параллельное ревью QA + UX командой агентов (только чтение).

## Соглашения

- Коммиты: `checkpoint: <что сделано>` для чекпоинтов; `feat:`/`fix:`/`test:`/`docs:`/`refactor:` для остальных. Ветка по умолчанию — `main`; для функции — ветка `feature/<коротко>`.
- Секреты и ключи подписи (`.env*`, `key.properties`, `*.jks`, `*.keystore`) не читать, не создавать в репозитории и не коммитить (запрещено в `.claude/settings.json` и `.gitignore`).
- Решения, влияющие на архитектуру или зависимости, фиксируются в `docs/decisions/NNNN-название.md` (контекст → решение → последствия → отвергнутые варианты).
